## 2. Эталон (часть A)

`scripts/whatif_ref.py` — независимая реализация FEATURE_SPEC на stdlib Python; это не код прототипа.
- Формула: гаверсинус, R = 6371008,8 м, вход [lon, lat], промежуточное `a` зажато в [0, 1], без округления.
- Кандидаты — все записи выбранной категории (`school` или `outpatient_clinic`) внутри bbox среза. QA-записи не удаляются, а помечаются (`COLOCATED`, `POSSIBLE_DUPLICATE`, `CATEGORY_DOUBT` из `evidence.js`).
- Правила:
  - `before` = минимум расстояний до кандидатов;
  - `after` = min(before, d_proj);
  - `delta` = before − after;
  - без проекта `after` = `before`, `delta` = 0;
  - без кандидатов `before` = null, `delta` = null, метка «В срезе нет исходных записей; улучшение не вычисляется»;
  - при ничьей выбирается меньший ID.
- Дополнительно по каждой точке вычисляется расстояние до ближайшей стороны bbox. Признак `edge_confound` = 1, если оно меньше `before`: тогда объект **вне** среза может оказаться ближе.
- Входы читаются байтами из Git по SHA:
  - `data.js` sha256 `bb2a7e66…`;
  - `evidence.js` sha256 `df736e98…`.

  Подробности — в `MANIFEST.json`.

Самопроверка `results/selftest.json`:
- 8 из 9 PASS: формула, инварианты на всех 17 строках, детерминизм, независимость от порядка при ничьей.
- Расхождение с `haversine` из `app.js` на 203 парах в bbox — ≤ 2,3·10⁻¹³ м.
- Одна проверка FAIL: в `app.js:79` нет требуемого спецификацией зажима `a` в [0, 1]. Внутри bbox это на числа не влияет. Это замечание к новому коду сборщика, а не ошибка эталона.

## 3. Задачи с вычислимыми ожидаемыми исходами

Полные сценарии `city-whatif-v1` и ожидаемые значения без округления — в `tasks/whatif_tasks.json`; краткая сводка — в `results/expected_summary.txt`. Числа ниже округлены до метра.

| ID | Город / категория | Что проверяется | Ожидаемый исход (ключевое) | QA-конфаунды |
|---|---|---|---|---|
| W1 | Шымкент / школа | базовый до/после/разница | cp1: 246 → 100 м, разница 146 м, источник «после» — проект; cp2: 244 м без изменений; cp3: 386 м без изменений | ближайшая к cp1 — `POSSIBLE_DUPLICATE` с ничьей из 2 записей; у cp3 `edge_confound` |
| W2 | Шымкент / школа | точка в координате двух записей | до = после = 0 м, выбрана запись `baeda67d…` (меньший ID), разница 0 | две записи в одной точке **без** QA-флага: правило дублей их не поймало |
| W3 | Шымкент / школа | ближайшая «школа» под сомнением | 33 м до «Реклама 42» (`CATEGORY_DOUBT`) | без QA-записей было бы 454 м: число зависит от одной сомнительной записи (диагностика, не значение продукта) |

| W5 | Астана / поликлиника | проект в точке контроля | cp1: после = 0, разница = до = 153 м, источник — проект; cp2: 19 м без изменений | 0 м до гипотетического объекта не означает реального учреждения |

Случай «в срезе нет записей категории» на реальных данных невозможен: обе категории есть в обоих городах. Он задан как **synthetic** unit-случай (W8) для функции расчёта сборщика.

## 4. Процедура A на SHA сборщика с функцией (будущий запуск)

1. Записать точный SHA сборки и sha256 `data.js` и `evidence.js`. Если отпечаток среза отличается от входов задач, сначала заново запустить `make_tasks.py` на новых данных. Старые ожидаемые числа к другому срезу не применяются.
2. Для каждой задачи W1–W7:
   - загрузить сценарий импортом JSON, если он реализован; иначе поставить точки вручную как можно ближе к указанным координатам;
   - выполнить шаги;
   - экспортировать сценарий с результатами.
3. Запустить `python3 scripts/compare_export.py <export.json>`. Сравнитель пересчитывает эталон **по координатам из самого экспорта**, поэтому неточность ручной постановки ложного FAIL не даёт. Затем он сверяет before/after/delta с допуском 0,5 м (вывод в метрах) и ID ближайших записей, если они экспортируются.
4. Вручную отметить по каждой задаче:
   - показан ли источник ближайшей записи и её QA-флаг (W1, W3, W4);
   - есть ли метка hypothetical (W1, W5, W6);
   - показано ли ограничение среза (W7);
   - восстановлен ли базовый вариант после удаления (W6);
   - при смене города или категории сбрасывается ли активный сценарий с причиной (спецификация, без расчёта).
5. W8: каждый недопустимый ввод отклонён с понятным сообщением, и активный сценарий не изменился частично.
6. Вердикт по каждой задаче — PASS, FAIL или NOT_RUN. Отсутствующий запуск не считается PASS.

Сравнитель проверен контролями (`results/compare_controls.json`): корректные экспорты по всем шагам W1–W7 → PASS; те же экспорты с искажением «после» на 25 м → FAIL.

## 5. План B: понимание пользователем (без участников и результатов)

- **Формат.** Формативное think-aloud исследование, 5–8 специалистов или аналитиков, не участвовавших в разработке. Только описательные итоги, без статистических обобщений.
- **Добровольное согласие**; персональные данные не записываются; запись экрана — только с согласия.
- **Вопросы с заранее известным правильным ответом** (порог «понял» фиксируется до сессий):
  1. W1: «Что означает разница 146 м?» Верно: расстояние по прямой до ближайшей записи в срезе уменьшилось. Неверно: время пути, доступность, качество обслуживания.
  2. W1/W5: «Является ли проект реальной школой или поликлиникой?» Верно: нет, это гипотетический объект.
  3. W3: «Можно ли считать, что школа в 33 м?» Верно: ближайшая запись помечена как сомнительная по категории; без неё было бы 454 м.
  4. W7: «Ближайшая школа города в 442 м?» Верно: неизвестно, вне среза может быть ближе.
  5. W2/W4: «0 м — школа прямо в этой точке?» Верно: координата точки совпадает с координатой записи; точное место не проверено.
- **Отчёт:** число верных ответов на каждый вопрос (k из n) и цитаты непонимания. Без процентов «понятности», пока нет реальных сессий.

## 6. План C: время выполнения (без участников и результатов)

- **Начало** — показ карточки задачи. **Конец** — устный ответ или явное «готово».
- Время фиксирует наблюдатель по локальным отметкам или журнал событий интерфейса без персональных данных, если сборщик его добавит.
- **Отчёт:** медиана и размах по каждой задаче, отдельно для первого и повторного выполнения.
- **Порядок задач** уравновешивается латинским квадратом.
- **Конфаунды:** think-aloud замедляет работу; обучение по ходу сессии; ручная постановка точек против импорта.
- Сравнение с другой версией интерфейса — только на одинаковых задачах и равных условиях.

## 7. Что протокол НЕ утверждает

- Функция на SHA `c58a3b2` не реализована, и с интерфейсом ничего не сверялось.
- Ожидаемые числа — свойство среза Overture в bbox. Это не расстояния до реальных учреждений города и не доступность.
- Части B и C — только план.
- T1 и его метрики к этой функции не относятся.
