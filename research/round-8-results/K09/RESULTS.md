# K09-R8. Результаты: жадный выбор против точного поиска (city-plan-v2)

Слот K09, раунд 8. Выводы относятся к **методу** (жадные эвристики против полного перебора), а не к городам. Все контрольные точки, кандидаты и стоимости — **synthetic**. Исходные записи — реальный срез Overture из `data.js` прототипа или пустое synthetic-условие. Интеграция в сборку (BUILD) **не проверялась и не утверждается**.

Полные таблицы: `results/tables.md` (генерируется `scripts/make_tables.py`); сырые строки — `results/runs.csv`, `results/scenarios.csv`.

## 1. Кратко

1. **G1 — сильный ориентир, но не оптимум.** G1 — жадный по ключу цели. В основной сетке он совпал с точным оптимумом в 84.1% задач по mean, 72.3% по minimax и 93.3% по coverage (n=2430 на ячейку). Среди нетривиальных задач, где точный план содержит не меньше двух объектов, — 81.7%, 68.1% и 92.2%.
2. **G2 заметно хуже G1 по всем трём целям.** G2 выбирает по отношению выгоды к стоимости. Совпадение полного ключа: 51.5% / 26.3% / 33.2%. Парный точный тест McNemar даёт p < 1e-180 для каждой цели. Совпадение только первичной метрики у G2 выше (53.0% / 73.3% / 81.1%): G2 не оптимизирует лексикографические вторичные ключи. В 94–99.7% промахов план G2 дешевле точного (post-hoc).
3. **Задача становится труднее для жадных методов:**
   - с ростом числа кандидатов (G1/mean: 90.6% → 82.1% → 79.5% при 6/10/16 кандидатах);
   - с ростом max_selected (вторичный анализ: G1/mean 100% → 73.3% → 66.7% при 1/2/5);
   - **без исходных записей** (synthetic-условие: G1/mean 58.0%, G1/minimax 32.8% против 95–99% и 87–97% со срезами).
   Срезы различаются плотностью существующих записей относительно bbox, поэтому это эффект условия задачи, а не города.
4. **Худшие случаи значимы.** Относительный разрыв G1:
   - mean — p90 0.025, максимум 0.787;
   - minimax — p90 0.176, максимум 1.762, то есть худшая точка в 2.76 раза дальше оптимальной.
5. **Время не оправдывает эвристику в пределах CORE_SPEC (≤16 кандидатов).** Точный перебор трёх целей за один проход (Python, этот контейнер):
   - медиана 8.1 мс при 16 кандидатах и max_selected=3;
   - 45.7 мс (p90 50.1 мс) при max_selected=5.
   G1 и G2 работают за 0.05–0.6 мс (медиана) на одну цель. В продукте при ≤16 кандидатах разумно показывать точный оптимум, а жадный результат — только как подпись «эвристика».

| Фактор | Уровни |
|---|---|

Генерация (`k09plan/suite.py`):
- точки и кандидаты равномерны в bbox среза;
- стоимость — целое число из [100, 1000] условных единиц;
- seed — строка, поэтому результат не зависит от PYTHONHASHSEED.

Алгоритмы:
- **exact** (`k09plan/exact.py`) — полный перебор допустимых подмножеств;
- **G1**, **G2** (`k09plan/greedy.py`) — описаны в `EXPERIMENT_DESIGN.md`. Ничьи: всегда меньший id.

Метрики разрыва (`k09plan/gap.py`):
- **hit** — совпадение полного ключа CORE_SPEC;
- **первичная метрика равна** — abs = 0;
- **rel** — только при положительном знаменателе exact; иначе null (26 задач coverage с covered = 0 у exact);
- **unknown_worse** не встретился ни разу.

Статистика:
- 95% интервал Уилсона;
- точный двусторонний McNemar по парам сценариев. Для p ниже наименьшего float в отчёт выводится log10 p, вычисленный на целых;
- квантили nearest-rank.

Время:
- `time.perf_counter`, минимум из 3 повторов;
- один процесс CPython 3.11.15, 4 CPU (`results/run_meta.json`).

Факторы. Полностью — `results/tables.md` §2. Главное:
- **Число кандидатов** — сильнейший фактор для обоих алгоритмов: G2/mean 78.4% → 47.7% → 28.5%; G1/minimax 85.7% → 69.8% → 61.5%.
- **Бюджет.**
  - G1 почти не зависит от бюджета: mean 83.2 / 83.1 / 85.9%.
  - G2 **ухудшается** при ослаблении бюджета: mean 60.9% → 49.0% → 44.7%; minimax 39.5% → 19.5% → 20.0%.
  - Нормировка на стоимость вредит, когда бюджет почти не ограничивает: в промахах G2 выбирает более дешёвый план (§4б в tables.md).
- **Веса.** Эффект слабее: G1/mean uniform 79.1%, one_heavy 89.5%.

Вторичный анализ (парный, n = 30 на уровень):
- **max_selected = 1** — оба алгоритма совпадают с exact в 100% случаев, как требует теория (см. §4).
- **max_selected = 2 и 5** — G1/minimax 50.0% и 46.7%; G2/minimax 10.0% и 0.0%.
- **Радиус** меняет только coverage. Mean и minimax одинаковы на всех уровнях, что подтверждает парный дизайн. G1/coverage: 100% → 90% → 70% при 100 / 300 / 800 м; G2/coverage: 50.0% → 13.3% → 0.0%.

## 4. Post-hoc анализ (не предрегистрирован, помечен отдельно)

**Нетривиальные задачи.** Если точный план содержит не больше одного объекта, оба жадных алгоритма гарантированно совпадают с exact (в основной сетке required пуст):
- G1 первым шагом берёт лучший одиночный план по ключу и не добавляет объект без строгого улучшения;
- G2 в конце сравнивает свой план с лучшим одиночным.

На данных это проверено утверждением (assert) в `scripts/make_tables.py`. Поэтому информативны задачи с размером точного плана ≥ 2: 2112–2115 из 2430.

| G2/mean | 44.3 (42.2–46.4) | 46.0 |

**Структура промахов** (§4б tables.md):
- при budget_ratio = 1.0 все промахи G1 имеют тот же размер плана, что exact, — это близорукий выбор, а не бюджет;

## 6. Интерпретация для диплома (о методе)

- Для учебного прототипа с лимитом CORE_SPEC ≤16 кандидатов точный перебор дёшев. Жадный ответ, подписанный как «оптимум», был бы неверен в 7–74% задач, в зависимости от цели и алгоритма.
- Жадные эвристики полезны:
  - как базовая линия;
  - как объяснение («какой объект даёт наибольший прирост первым»);
  - для задач больше 16 кандидатов. Последнее здесь **не проверено**, и переносить выводы на большие n нельзя.
- minimax (худшая точка) — самая трудная цель для жадного выбора: прирост по максимуму часто нулевой, пока не закрыта самая дальняя точка.
- Нормировка на стоимость (G2) не помогает при свободном бюджете. Для бюджетных задач нужна другая конструкция. Например, перебор пар или троек плюс жадное дополнение — такие варианты здесь не проверялись. Библиографическая проверка соответствующих гарантий в этом раунде не выполнялась (нет доступа к научным хостам).

## 7. Ограничения и угрозы валидности

- **Synthetic-данные.** Точки, кандидаты и стоимости synthetic, генерация равномерная в bbox среза. Веса — приоритет, а не население. Радиус — параметр, а не норматив. Реальные «пользовательские точки» могут быть кластеризованы, и тогда доли совпадений будут другими.
- **Срезы.** Срезы — ограниченные bbox Overture с неизвестной полнотой. Различия срезов — это различия плотности исходных записей, а не свойства Астаны или Шымкента. Условие nobase — synthetic.
- **Строгость метрик.** hit — строгая метрика полного ключа. Для G2 она частично наказывает за неоптимизированные вторичные ключи, поэтому рядом приводится «первичная метрика равна».
- **Вариант G2.** G2 — один конкретный вариант ratio-greedy с проверкой лучшего одиночного кандидата. Другие варианты (частичный перебор, локальный поиск) не исследовались.
- **Время.** Замеры времени сделаны на одной машине, в Python. Поведение JS-реализации сборщика этим не измерено.
- **Масштаб.** Число кандидатов не больше 16. Вторичный анализ — n = 30 на уровень, интервалы широкие.
- **Post-hoc.** Разделы §4 и §4б — post-hoc, гипотезы о механизмах не проверены экспериментом.
