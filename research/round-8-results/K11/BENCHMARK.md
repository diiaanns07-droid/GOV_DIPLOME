# K11 round 8, этап 2 — бенчмарк отзывчивости 16 кандидатов × 25 точек

**Это измерения одной машины, а не SLA.**
- Linux-контейнер, 4 vCPU Intel Xeon 2.10 GHz.
- Node v22.22.0.
- Headless Chromium 141.0.7390.37 (Playwright 1.56.1).

Данные: `syn_bench_16x25.json` (синтетика) и `real_shymkent_school_16x25.json` (исходные записи среза `a5b5e2d` + синтетические точки и кандидаты). Полный перебор: 65 536 подмножеств; с чувствительностью к бюджету — 4 перебора.

Команды:

```bash
node --expose-gc bench/bench_node.cjs --repeat 7 --out runs/stage2_bench_node.json
NODE_PATH="$(npm root -g)" node bench/bench_browser.cjs --repeat 5 --out runs/stage2_bench_browser.json
```

Выброс не скрыт.

## 2. Дефект, найденный бенчмарком, и исправление

Первая версия worker уступала цикл событий через `setTimeout(0)` после каждых 4096 масок. В браузере вложенные таймеры зажимаются до ≥ 4 мс, и поиск в worker шёл в 4–5 раз дольше синхронного.

Исправление в `src/plan_worker.js`:
- кванты по времени (`slice_ms`, по умолчанию 8 мс);
- уступка через `MessageChannel` (браузер) или `setImmediate` (Node).

| Браузер, медиана мс | до | после |
|---|---:|---:|
| синтетика, тёплый worker, с чувствительностью | 331.2 | 73.6 |
| синтетика, холодный worker, с чувствительностью | 352.9 | 117.4 |
| срез Шымкента, тёплый worker, без чувствительности | 66.6 | 27.5 |

Блокировка главного потока не ухудшилась. Отчёты «до»: `runs/stage2_bench_*_before_fix.json`.

Второй дефект проявился после квантов по времени. Иногда задача завершалась раньше, чем worker читал `cancel`; подтверждения не было, и оркестратор через grace-период жёстко убивал исправный worker: в браузере 4 из 5 при отмене на 90 %, а Node-бенчмарк падал с «no cancel ack». Исправление: `cancel` для уже не выполняемого запроса подтверждается сразу. Тест 12 в `tests/harness.cjs` ловит прежнее поведение (проверено порчей).

Один поиск 16×25 держит ≈ 1.4 МБ кучи: матрицы расстояний и карта Парето на 3 995 пар.

`tests/harness.cjs` завершается сам, без `process.exit`. Это подтверждает, что ни worker, ни таймеры не остаются.

## 5. Выводы для BUILD

- **По умолчанию `mode: "auto"` (worker) с одним переиспользуемым runner.** Холодный старт дорог: в браузере +30–45 мс, в Node +65–70 мс. Не создавать runner на каждый запуск.
- **Чанки (`sliceMs: 8`) — рабочий запасной путь**, например если worker недоступен. Длинных задач нет, общее время близко к синхронному, но таймеры опаздывают до ≈ 17 мс: хуже, чем у worker.
- **Синхронный `optimizePlansSync` для UI не годится:** на 16×25 с чувствительностью он даёт длинные задачи 74–84 мс.
- **Пороги здесь не универсальны.** Слабая машина или другой браузер требуют повторить `bench/bench_browser.cjs`.
