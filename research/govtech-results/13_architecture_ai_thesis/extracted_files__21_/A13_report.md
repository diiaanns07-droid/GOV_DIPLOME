## Резюме (≤200 слов)

Репозиторий STUPITS я клонировал и **реально запустил**: коммит `834a25f` от 2026-09-23. Прошли все 112 тестов, `check.py` выдал «все 12 проверок пройдены». Оптимизатор воспроизводит 57.24 за 0.57 с, локальный API отвечает.

- Для Шымкента надо переносить **архитектуру** (данные → расчёт → доказательство → объяснение), а не числа. Эффекты мер, веса и QoL Score синтетические, это признано в README.

**Ограничение:** прокси моей среды блокирует gov.kz, stat.gov.kz, data.egov.kz, doi.org, Crossref, SUMO и Overpass (`x-deny-reason: host_not_allowed`). Поэтому официальных данных Шымкента я **не проверял**. Научные источники даны как непрочитанные кандидаты из памяти.

**Лучший следующий шаг:** ввести контракт `data_version` с полем `kind` у каждого значения и запустить шымкентский профиль «только наблюдаемые показатели без Score». Темы диплома, которые реализуемы уже сейчас: T1 (проверяемый советник) и T2 (поручение → ограничения).

## 1. Что реально есть в STUPITS (observed, запуск)

- **Стек.** Python 3.11–3.14, numpy, HTTP-сервер на стандартной библиотеке (`ThreadingHTTPServer`), фронтенд на чистом HTML/JS с локальным MapLibre 5.6.2. Советник через OpenAI-совместимый API и jsonschema. Сборки и БД нет (README; `ui/web_server.py:11`).
- **Модель** (`data/city_data.json`). 5 районов, 10 показателей по шкале 0–100, 14 мер, 3 синергии, несовместимости, бюджет 100 у.е., горизонт 8 кварталов, порог критичности 40. Формула: `Score = 0.7·D_avg + 0.3·min D − 1·N_crit`. В README прямо сказано: «Данные синтетические… не откалиброваны».
- **Воспроизводимость (мой запуск).** 112 тестов прошли за 13.1 с. `check.py` завершился с exit 0. Через API получено: база 52.56, пример ТЗ 56.54 за 0.002 с, лучший план 57.24 за 0.57 с. Пространство поиска: 2002 набора, из них 1181 проходят правила, 1 407 050 сценариев, допустимых 694 395.
- **Граница LLM, которую стоит сохранить.** Ответ советника собирается из отчёта движка. Из текста LLM вырезаются предложения с числами и числительными (`agent/evidence.py`). Действуют лимиты: 4 запроса к LLM и 6 вызовов движка на ответ. Без ключа работает офлайн-разбор (мой запрос к `/api/advisor`: 200, ответ за 0.07 с).
- **Безопасность сервера.** POST-запросы с чужим заголовком `Host` отклоняются (мой запрос дал 403). Тело запроса ограничено 128 КБ (`MAX_BODY`), по умолчанию сервер слушает только 127.0.0.1. Хранения на сервере нет, состояние живёт в `sessionStorage`.
- **Где модель привязана к Астане.** Движок от названий не зависит: в `engine/` нет ни одного вхождения «Астан». Привязка сидит в советнике и UI: `nura_priority` в `agent/advisor.py:114`, «помощник акима Астаны» в `agent/prompts.py:10`, путь к `astana_districts.geojson`, примеры с `nura` в тестах.
- **Дефекты происхождения данных.**
  - `real_context_meta.json` содержит `status: unavailable` и `districts_source: fallback_approx`, а `real_context.json` при этом хранит нули по всем категориям. Это нарушает правило «нет данных ≠ 0». В UI и движке файл, судя по grep, не используется.
  - GeoJSON районов взят из OSM (ODbL) с метаданными запроса и проверкой топологии. Это хороший образец provenance.
- **Лицензии.** Файла лицензии в корне нет. Для GovTech и открытого диплома это нужно решить: какая лицензия, чьи права, не было ли других членов команды.

## 2. Разрыв между учебной моделью и Шымкентом

1. **Показатели.** У десяти индексов 0–100 нет измеримого источника. В ТЗ, однако, есть операциональные определения, и их можно превратить в реальные метрики. Пример: T2 «100 = все жители в 500 м от остановки с интервалом ≤10 мин» — это доступность по OSM-остановкам и расписанию (`docs/tz/tz_data_and_rules.txt`). Источник расписания для Шымкента не найден (open question).
2. **Эффекты мер (`e_mk`), лаги и стоимости** придуманы для задания. Для Шымкента это `scenario_param` с диапазоном, а не `observed`.
3. **Веса и формула Score** — нормативный выбор организатора хакатона. Публиковать «Shymkent QoL Score» без обоснования нельзя. Сначала нужны показатели по отдельности, а любой композит должен быть подписан как сценарный индекс с явными весами и анализом чувствительности.
4. **География.** Состав районов Шымкента (я помню 5 районов, включая выделенный позже Туранский) — **гипотеза**, её нужно сверить с официальным источником. Границы и показатели требуют версии с датой, потому что границы менялись.
5. **Масштаб.** Если опуститься ниже районов (микрорайоны, сельские округа, участки), полный перебор перестаёт работать (раздел 4, E2).

## 3. Целевая схема: city → geography/data_version → domain_model → scenario → computed_result → evidence → explanation

```
City(id, name, timezone)
 └─ DataVersion(id, city_id, created_at, geography_version, status: draft|reviewed|frozen, hash)
     ├─ GeographyVersion(id, units[], source_refs[], valid_from, valid_to)
     ├─ Observation(indicator_id, unit_id, period, value|null, unit, kind, source_refs[], derivation|null)
     └─ DomainModel(id, version, kind: "training"|"scenario"|"calibrated", parameters[], formula_ref)
          └─ Scenario(id, data_version_id, model_id, decisions[], event_id|null, constraints, params_override)
               └─ ComputedResult(hash(scenario+model+data_version+engine_version), outputs, engine_version)
                    └─ EvidenceRef[] → Observation/ScenarioParam/Source
                         └─ Explanation(text, llm_model|null, numbers_from: "engine", stripped_claims[])
```

Ключевые правила:
- **`kind` у каждого числа:** `observed | derived | scenario_param | synthetic`.
- **Защита от смешивания.** Движок отказывается помечать результат как «оценку города», если среди входов есть `synthetic`. Такой результат получает метку `mode: training`.
- **Идентификатор результата** — это хэш входов. Повтор даёт тот же `result_id`, и кэш работает бесплатно.
- **Модели городов не смешиваются.** Астана-ТЗ замораживается как `city=astana, model=astana-tz-2026, kind=training`. Шымкент стартует с `kind=scenario` без Score.

**Минимальные контракты**, JSON-фрагменты (это контракты, а не реализованный код):

```json
{"observation": {"id":"shy-2025-S2-al-farabi","indicator_id":"clinics_per_10k","unit_id":"shy-d-02",
  "period":"2025","value":null,"unit":"шт/10 тыс. жит.","kind":"observed",
  "source_refs":[{"source_id":"A0X-S00Y","locator":"табл. 3, строка 5"}],"note":"null = не найдено, не ноль"}}
{"scenario_param": {"id":"M8.S2.effect","value":{"low":5,"mid":10,"high":15},"kind":"scenario_param",
  "justification":"hypothesis","source_refs":[]}}
{"computed_result": {"result_id":"sha256:…","engine_version":"git:834a25f","data_version":"astana-tz-2026@frozen",
  "outputs":{"score":56.54},"inputs_kind_summary":{"synthetic":134,"observed":0},"mode":"training"}}
```

**API v2 (предложение).** Старые `/api/*` остаются алиасом Астаны-ТЗ, и UI не переписывается.

| Метод | Назначение |
|---|---|
| `GET /api/v2/cities` | список городов и версий |
| `GET /api/v2/{city}/{data_version}/bootstrap` | данные для текущего UI плюс `kind`, provenance и бейдж режима |
| `POST /api/v2/{city}/{data_version}/simulate` | синхронно, быстро |
| `POST /api/v2/{city}/{data_version}/optimize` | синхронно при малом пространстве; при большом возвращает `202 job_id` |
| `GET /api/v2/results/{result_id}` | кэш по хэшу |
| `GET /api/v2/evidence/{source_id}` | карточка источника |

Ключ не нужен для любых расчётов и чтения. LLM — отдельный необязательный эндпоинт.

**Хранение по потребности.**
1. Сейчас: JSON и GeoJSON в git, `data_version` = тег плюс SHA-256 файлов. Этого хватает для 5–10 районов.
2. Когда появятся временные ряды и несколько версий: SQLite или DuckDB с GeoParquet в одном файле.
3. Когда понадобятся многопользовательская правка и пространственные запросы на сервере: PostGIS.

Миграция между уровнями механическая, если с первого дня соблюдать контракт Observation.

**Ограничения текущего сервера для публичного сайта.**
- `ThreadingHTTPServer` и `optimize_lock` выстраивают тяжёлые запросы в очередь. Это видно в E3.
- Нет rate limit, аутентификации, кэша результатов и журнала аудита.
- Нет HTTPS: его даёт обратный прокси.

Для пилота достаточно поставить сервер за reverse proxy, добавить кэш по `result_id` и лимит частоты запросов. Переход на ASGI-фреймворк не обязателен до появления фоновых задач.

## 6. Модули и постепенный план

**Независимые модули (предварительно):**
1. `registry`: города, версии, источники.
2. `ingest`: загрузчики с provenance; нет данных — значит `null`.
3. `indicators`: формулы derived-показателей, например доступность в радиусе.
4. `engine` (существующий) с адаптером под `DataVersion`.
5. `optimizer`: перебор и опционально MILP с перекрёстной проверкой.
6. `scenarios` и `results-cache`.
7. `evidence`: карточки источников.
8. `explainer`: LLM опционально, офлайн-шаблон.
9. `docsearch`: BM25, затем опционально RAG.
10. `eval-harness`: наборы, метрики, отчёты.
11. `web`: существующий UI плюс бейдж режима и переключатель города.

**Без переписывания UI:**
- Шаг 1: заморозить Астану-ТЗ как версию.
- Шаг 2: `bootstrap` получает поля `kind` и `mode`, а UI показывает бейдж «учебная модель».
- Шаг 3: второй город загружается тем же форматом. Карта читает `geojson_url` из bootstrap вместо зашитого пути.
- Шаг 4: советник получает имя города и приоритеты из данных, а не из `nura_priority` и промпта.

**Три уровня амбиций (мой срез — техплатформа):**

| Уровень | Что | Данные и ресурсы | Проверяемое предположение | Самый дешёвый тест «стоит ли продолжать» |
|---|---|---|---|---|
| Прототип (дни) | Мультигородной движок с provenance. Шымкент показан **только наблюдаемыми** показателями, без Score. Астана — учебный режим | 1–3 реальных агрегата по районам Шымкента от A01–A12 и границы | Контракт `kind`/`source_refs` не ломает UI и тесты | Ветка, где Астана проходит 112 тестов плюс тест «synthetic не может получить mode=city» |
| Продукт (1–3 мес.) | «Проверяемый городской советник»: C и D с метриками, B для импорта статистики, сценарии с диапазонами параметров и анализом чувствительности | Набор поручений от реальных пользователей; размеченная выборка документов | Ограничения от LLM дают меньший регрет, чем форма или парсер, на отложенном наборе | 30 поручений от 3–5 человек, не видевших каталог-парсер; сравнение C против baseline |

Как применять: 1–2 — методология GIS-MCDA и чувствительности весов; 3–4 — почему системы поддержки планирования не внедряются (implementation gap), то есть аргумент против «просто сделать сайт»; 5–6 — устойчивый выбор при глубокой неопределённости; 7–10 — проверяемость и уязвимости LLM; 11–12 — перевод текста в оптимизационную модель.

**Т1. Проверяемое объяснение решений городской модели.**
- **Гипотеза.** Конвейер «инструмент → отчёт кода → комментарий LLM с фильтром чисел» снижает долю неподтверждённых числовых утверждений по сравнению с LLM, получившим те же данные в промпте. Полезность для пользователя при этом не уступает шаблону по слепой оценке.
- **Протокол.**
  - Условия: (a) шаблон (`agent/offline.py`), (b) LLM с данными в контексте без инструментов, (c) текущий конвейер.
  - Вопросы: 60 штук от 3+ людей, 20 из них отложены и не используются при настройке промптов.
  - Метрики: unsupported-claim rate (ручная разметка двумя людьми, κ), Likert-полезность вслепую, время ответа.
- **Данные.** Учебная модель Астаны: проверяется верность инструменту, а не реальность.
- **Ограничения.** Результат зависит от модели и даты; выводы о реальных решениях акимата не делаются.
- **Пригодность для одного разработчика:** высокая.

**Т2. Перевод поручений в валидируемые ограничения.**
- **Гипотеза.** На отложенном наборе LLM с JSON-схемой и валидатором движка даёт меньший регрет решения, чем словарный парсер и форма, особенно на двусмысленных и невыполнимых поручениях. Это нужно проверить, а не обещать.
- **Протокол.**
  - Набор: 100+ поручений от людей, не знающих парсер; классы — простые, составные, двусмысленные, невыполнимые; заморозка до экспериментов.
  - Условия: парсер (E4) против LLM против LLM с одним уточняющим вопросом.
  - Метрики: exact match, slot-F1, доля принятых движком, регрет = Score(gold-constraints optimum) − Score(pred-constraints optimum, оценённый без нарушений gold), корректность отказа на невыполнимых.
- **Данные.** Каталог мер, синтетический допустим. Перенос на Шымкент — второй каталог.
- **Пригодность:** высокая. Харнесс уже прототипирован (E4).

**Т3. Устойчивость ранжирования портфелей мер к неопределённости параметров.**
- **Гипотеза.** При реалистичных диапазонах весов и эффектов топ-план «max Score» часто меняется, а планы minimax или regret устойчивее. Значит, интерфейс должен показывать диапазон, а не точку.
- **Протокол.**
  - Монте-Карло по параметрам (диапазоны — hypothesis с обоснованием).
  - Метрики: частота смены топ-1, Kendall τ топ-10, regret.
  - Сравнение критериев: max E[Score], minimax, min-regret.
  - Дополнительно: MILP-формулировка, проверенная на совпадение с перебором для 5×14 (оптимум 57.24) и масштабируемая на мелкую сетку.
- **Данные.** Учебная модель плюс реальные диапазоны из A01–A12, если найдутся.
- **Ограничения.** Без калибровки выводы методические, а не про Шымкент.
- **Пригодность:** средне-высокая. Вычисления дешёвые, а MILP требует OR-Tools или PuLP.

Новизну я не утверждаю: сопоставление с литературой не выполнено.

## 11. Три сильных возражения против моей рекомендации

1. **«Платформа раньше пользы».** Контракты и provenance — инженерная гигиена, которую жюри может не оценить. Возможно, выиграет узкий полезный сервис для одной отрасли, даже без универсальной схемы.
2. **«Синтетическая модель — слабая база для диплома».** Комиссия может счесть эксперименты на учебном городе нерелевантными. Ответ: измеряется верность инструменту, а не город. Но риск реален, и Т3 без калибровки — методическая работа.
3. **«Проверяемый AI уже решён».** Фильтр чисел и tool-calling существуют в литературе и индустрии. Без сопоставления с RAG и citation-литературой (ALCE и др.) научный вклад Т1 может оказаться нулевым. Отсюда выбор Т2 как более узкой и измеримой темы.
