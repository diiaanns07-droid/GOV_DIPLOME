## 4. MVP: «Навигатор по публичным документам территории + проверка полноты сведений»

### 4.1. Пользователь, решение, входы, результат

| | Содержание |
|---|---|
| Основные пользователи | (1) житель или предприниматель МСБ, который собирается подать заявку на участок или купить лот; (2) студент-архитектор или дипломник; (3) сотрудник ЦОН/акимата, который консультирует (вторично) |
| Решение пользователя | «Какие документы и процедуры применимы к этой территории, что уже известно публично, чего не хватает и у кого это запросить» |
| Входы | уровень территории (район/квартал/участок); при наличии — кадастровый номер, **введённый пользователем** (система номер не генерирует); цель (жильё/торговля/производство) |
| Результат | (а) список применимых документов со статусом и локатором; (б) карточка территории: по каждой теме — статус сведений, акт, юридический вес геометрии, кто даёт обязывающий ответ; (в) список запросов, которые пользователь может отправить сам |
| Чего MVP не делает | не говорит «можно строить»; не определяет границы; не показывает правообладателей; не заменяет АПЗ, идентификационный документ, решение акимата |
| Метрики пользы | доля ответов, где найден **действующий официальный** документ с правильным локатором (по эталону); время до нахождения в сравнении с обычным поиском; доля тем со статусом `not_checked` после работы; число ошибок вида «проект выдан за действующий» (цель — 0) |

### 4.2. Где AI, а где нет

- **Без AI (основа):** реестр документов, проверка полноты, правила статусов, стили карты по юридическому весу. Эксперимент §8 показывает, что проверку полноты выполняют правила.
- **AI (опционально):** (1) отнести свободный вопрос к одному из N сценариев; (2) составить ответ **только** из записей реестра со ссылками `{{eN:/path}}` — как в STUPITS; (3) во втором уровне — извлекать реквизиты из PDF-актов со статусом `llm_human_checked` после проверки человеком.
- **Базовая линия без AI:** FAQ + фасетный поиск по реестру. Если на эталонных вопросах AI не превосходит её по точности, AI не нужен.
- Запрещённые формулировки советника фильтруются правилом: «разрешено строить», «участок свободен», «ограничений нет» без статуса `not_applicable_confirmed`.

### 4.3. Где нужны заверенные границы и решение органа

| Вопрос пользователя | Что даёт помощник | Что требует заверенных данных | Чьё решение обязательно |

## 5. Схема карточки территории (контракт A11 v0.1)

Полный контракт — файл `A11_territory_card.schema.json` (JSON Schema 2020-12). Ключевые поля по каждой теме:

| Поле | Назначение |
|---|---|
| `topic` | одна из 17 тем: категория, целевое назначение, кадастровый статус, зона генплана, статус ПДП, красные линии, зоны ЛЭП, газа, прочих сетей, водоохранная, СЗЗ, наследие, приаэродромная, сейсмика, подтопление, аукцион, зона платы |
| `status` | found_official / found_official_draft / found_unofficial / not_public / not_found / not_checked / not_applicable_confirmed |
| `legal_basis` | норма, из которой ограничение вообще возникает (вид, орган, номер, дата, статус, URL, локатор, дата проверки текста) |
| `establishing_act` | конкретный акт для этой территории (постановление акимата, решение маслихата, утверждённый план, ТУ, проект, новость) |
| `geometry.source_type` / `legal_weight` | certified_cadastral, approved_plan_vector, approved_plan_raster_georef, derived_buffer, osm_context, none / legally_certified, illustrative, context_only, none |
| `authority_for_binding_answer` | кто даёт юридически значимый ответ |
| `provenance` | source_ids, accessed_at, extracted_by (human / rule / llm_human_checked / llm_unchecked) |

Контракт запрещает кадастровый номер в `card_id` и город, отличный от Шымкента (проверено отрицательными тестами, §8).

## 7. Сценарий демонстрации на открытых неперсональных данных (5 минут)

1. **Вводный экран.** «Шымкент → район» по полигону OSM (ODbL) с плашкой «граница OSM, не юридическая». Данные по Шымкенту ещё не загружены: Overpass заблокирован в этой среде.
2. **Вопрос:** «Хочу открыть магазин на участке в этом районе — что проверить?» Навигатор показывает путь: процедура (ЗК + госуслуга), документы района (генплан, ПДП — со статусом), список тем для проверки. Каждая строка — запись реестра со ссылкой и датой проверки.
3. **Карточка квартала.** Реальные документы из реестра + синтетический квартал SYN-Q1: полнота 2 из 11 тем, флаги «проект ≠ действующий», «акт утратил силу», «геометрия иллюстративная», «извлечено LLM без проверки».
4. **Планируемое изменение.** Проект ПДП/генплана показывается отдельным слоем «на обсуждении» со ссылкой на источник публикации.
5. **Список запросов.** Текст, который пользователь может отправить сам через eOtinish; система ничего не отправляет.
6. **Финал.** Таблица «что нужно заверить и кто решает» (§4.3).

Если подробные данные закрыты, демонстрация остаётся полезной на уровне регламентов: процедуры, сроки, ответственные органы, статусы документов — без геометрии участков.

## 8. Изолированный эксперимент: проверка полноты без LLM [S]/[D]

**Проверяемое предположение:** полноту публичных сведений о территории можно оценить детерминированными правилами, а LLM для этого не нужен.

- Среда: Python 3.12.3, jsonschema 4.26.0 (установлен из PyPI в песочнице).
- Файлы: `A11_territory_card.schema.json` (md5 d7be499c…), `A11_synthetic_card.json` (md5 bbc51a21…), `A11_completeness_check.py` (md5 58d566e3…).
- Команда: `python3 A11_completeness_check.py A11_territory_card.schema.json A11_synthetic_card.json` (дата проверки зафиксирована: 2026-10-04).
- Правила: R1 — «найдено официально» требует ссылки на действующий акт (R1b — нужен локатор); R2 — проект или новость показываются как планируемое и не засчитываются; R3 — иллюстративная или контекстная геометрия получает флаг (R3b — юридический вес у неподходящего типа геометрии); R4 — `llm_unchecked` не засчитывается; R5 — проверка источника старше 90 дней.
- Формула [D]: `completeness = count(обязательные темы со статусом found_official | not_applicable_confirmed, прошедшие R1, R3b, R4, R5) / count(обязательные темы уровня)`.

**Фактический результат (синтетика, не Шымкент):** засчитано 2 из 11 тем (0.182); 8 флагов; 9 запросов к органам, в том числе: `water_protection_zone — не засчитано: R1,R5`, `red_lines — не засчитано: R4`, `pdp_status — R2`, четыре темы `not_checked`. Отрицательные тесты: город «Туркестанская область» отклонён схемой; `card_id` в виде кадастрового номера отклонён схемой.

**Вывод:** правила работают и отделяют проекты, устаревшие и непроверенные извлечения. Ограничение: список обязательных тем и сами правила — моя гипотеза, их нужно сверить с законодательством во втором проходе. Индекс полноты — это мера **публичности сведений**, а не пригодности участка.

1. **[O]** Песочница исследования: все официальные домены РК и OSM — `host_not_allowed`.
2. **[O, со слов координатора]** data.egov.kz: прямое открытие завершилось ошибкой.

4. **[H]** Публичная кадастровая карта — интерактивная, без документированного открытого API и лицензии на массовую выгрузку. Скрейпинг недопустим до проверки условий.
5. **[H]** Генплан и ПДП: частичная публикация, растр без координат, возможное ограничение распространения топоосновы.

**Метод-опоры** (по памяти; веб-поиска и доступа к базам нет, библиографию нужно проверить):

- INSPIRE Data Specification on Land Use (Planned Land Use): элементы зонирования и дополнительного регулирования, атрибуты юридической природы регулирования, стадии процесса (разработка, утверждение, в силе, утратил силу) и ссылка на официальный документ. Применимо как образец полей статуса и юридического веса. Ограничение: правовой контекст ЕС, тяжеловесность.
- Bartik, Gupta, Milo — исследование 2024 г. о генеративном измерении регулирования (LLM отвечают на фиксированные вопросы по текстам муниципальных правил зонирования США, результат сверяется с данными, размеченными людьми). Применимо как метод «вопросник + валидация». Ограничения: англоязычные тексты хорошего качества, ошибки на сложных вопросах.
- Реальное внедрение: Нидерланды — публикация пространственных планов в машиночитаемом стандарте (ruimtelijkeplannen.nl, далее DSO по закону Omgevingswet с 2024). Работает благодаря правовой обязанности публиковать в стандарте, поэтому без такого мандата не переносится.

## 13. Три сильных возражения против рекомендации

1. **Ценность держится на ручной курации.** Без официального потока данных реестр устаревает. Один разработчик не обеспечит юридическую актуальность, а устаревший ответ о земле вреднее отсутствия ответа. Смягчение: даты проверки, правило R5, узкий охват — но риск остаётся.
2. **Восприятие и ответственность.** Даже с оговорками пользователи будут читать карточку как заключение. Жюри GovTech может увидеть дублирование сервисов Госкорпорации и акимата, а тема земли чувствительна к коррупционным рискам и ошибкам.
3. **Ключевые трудности не подтверждены.** Если у Шымкента уже есть единый геопортал с ПДП, зонами и лотами, MVP дублирует его. Тогда остаётся только навигатор по процедурам — или отказ от направления в пользу других сфер.
