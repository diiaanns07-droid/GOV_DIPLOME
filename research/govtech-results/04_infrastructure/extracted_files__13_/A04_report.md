## Резюме

В этой сессии нет веб-поиска и браузера, а сетевой прокси песочницы отвечает `403 host_not_allowed` на все целевые домены: stat.gov.kz, data.egov.kz, gov.kz, adilet.zan.kz, Overpass, Geofabrik, WorldPop, GHSL, HDX, 2GIS, geoBoundaries. Это ограничение моей среды, а не признак недоступности сайтов. Поэтому проблемы Шымкента ниже даны как **гипотезы с планом проверки**, а не как установленные факты.

Реально проверено три вещи. Первая — репозиторий STUPITS, коммит `834a25f`. В нём уже есть заготовка подсчёта объектов OSM по районам; её последний прогон упал по таймауту Overpass и записал нули, которые означают «нет данных». Вторая — открытых геоданных по Шымкенту на GitHub нет. Третья — синтетический эксперимент. В нём при пороге 500 м прямой радиус «покрывает» 67 % населения, а сеть улиц — 45 %. При 800 м район покрыт на 83 %, а «микрорайон» за барьером — на 26 %. Лучший участок для нового объекта меняется при смене порога.

Рекомендуемый MVP — сетевая пешеходная доступность одного вида объекта с разбивкой по микрорайонам и сравнением 2–3 участков. Для самого расчёта AI не нужен. Лучший следующий шаг — второй проход с веб-доступом: выгрузить OSM-экстракт и официальный реестр ПМСП или детсадов, проверить норматив и население.

## 2. Что важно в существующем продукте (проверено по коду)

1. **Готовая точка входа для доступности.** `fetch_real_context.py` одним запросом Overpass скачивает объекты 5 категорий по рамке города: `amenity=school`, `amenity=kindergarten`, `amenity=clinic|hospital` и `healthcare=*`, остановки, `leisure=park`. Затем раскладывает их по районам «точка в полигоне», с дедупликацией 25–150 м. Источник: строки 1–25 и `data/real_context_meta.json → category_tags`. В «Планах развития» README прямо написано: использовать этот слой «в экспериментальном индексе доступности».
2. **Нули вместо «нет данных».** В `real_context_meta.json` стоит `status: "unavailable"` от 23.09.2026, ошибка `ReadTimeout` к overpass-api.de. При этом `real_context.json` содержит 0 по всем районам и категориям (строки 364–372). Потребителей файла в .py/.js нет, так что в UI нули не попадают. Но для Шымкента этот шаблон опасен: в новом слое нужно писать `null` и статус, а не 0.
3. **Хороший шаблон происхождения данных.** `docs/GEO_SOURCES.md` и `data/astana_districts.geojson` (6 полигонов OSM, дата загрузки, лицензия ODbL, `scoring_enabled=false` для Сарайшыка). Это готовый контракт, который стоит повторить для слоёв Шымкента.
4. **Эффекты M1–M14 синтетические.** Например, M1: стоимость 18 у.е., эффекты T1 +6, T2 +9. README прямо называет данные синтетическими. В реальную доступность Шымкента их не переносить. Вместо фиксированного эффекта меры нужен **вычисляемый** прирост покрытия.
5. Упоминаний Шымкента в репозитории нет.

## 4. Генплан и программы: какую матрицу статусов заполнить во втором проходе

Проверить действующие документы я не смог. Предлагаю обязательную классификацию каждого объекта, чтобы не смешивать обещание с фактом:

| Статус | Минимальное доказательство |
|---|---|
| действующий | объект есть в официальном реестре или на картах, есть адрес, работает |
| строящийся | разрешение или уведомление о начале СМР, договор госзакупки, фото или новость с датой |
| запланирован | утверждённый документ (генплан, ПДП, План развития, бюджетная программа) с реквизитами и источником финансирования |
| обсуждается | заявление, новость, презентация без утверждённого документа |

Что установить. По памяти модели, всё ниже требует проверки:
- реквизиты действующего генплана Шымкента: акт, дата, горизонт. Для городов республиканского значения его, вероятно, утверждает Правительство;
- корректировки генплана после получения статуса республиканского значения (июнь 2018 года, по памяти) и после образования района Туран (около 2021 года, по памяти);
- завершённый План развития города на 2021–2025 годы и новый документ на 2026–2030 годы в рамках Системы государственного планирования;
- перечень ПДП по новым массивам;
- граница города: что сейчас город, а что Туркестанская область. Ряды БНС до 2018 года относятся к городу в составе прежней Южно-Казахстанской области, поэтому возможен разрыв ряда.

## 5. Район против микрорайона: где агрегат скрывает проблему

Реальную проверку на Шымкенте сделать не удалось. Механизм показан на синтетике, раздел 11: при пороге 800 м по сети район покрыт на **83,3 %**, а «микрорайон SE» за ж/д барьером и промзоной — на **26,2 %**. По прямому радиусу у того же SE было бы 52,6 %, то есть радиус вдвое завышает и без того плохую цифру. Средневзвешенное расстояние по всему району почти не чувствует, где именно стоит новый объект: 533–537 м для всех трёх участков. Поэтому средние по району — плохая метрика для приоритетов.

Почему это вероятно для Шымкента (гипотеза): районы, видимо, крупные и смешанные — центр с многоэтажками и периферия с ИЖС. Официальная статистика публикуется в основном на уровне города и района, а население микрорайонов, вероятно, открыто не публикуется (проверить). Значит, микрорайонный уровень придётся строить на сеточном населении. Если границ микрорайонов нет, нейтральная единица — H3-ячейка; можно дополнительно ставить подпись ближайшего `place=*` из OSM.

**Проверка во втором проходе:** для одного типа объекта посчитать `C(T)` по каждому из 5 районов и по каждому микрорайону или ячейке. Затем вывести пары, где разрыв `C_район − C_микрорайон` больше 30 п.п. и непокрытое население больше заданного минимума.

## 6. MVP: поиск зон плохой доступности и сравнение 2–3 участков

### 6.1 Пользователь и решение
- **Основной пользователь:** аналитик, который готовит обоснование размещения соцобъекта (управление здравоохранения, образования или архитектуры акимата), либо депутат маслихата или НКО, проверяющие обоснование.
- **Решение:** (а) какие микрорайоны хуже всего обеспечены объектом вида X в пешей доступности; (б) какой из 2–3 участков-кандидатов даёт наибольший прирост покрытия и насколько этот выбор устойчив к неопределённости данных.
- **Результат:** карта покрытия по сети, таблица по микрорайонам, таблица участков с диапазонами по сценариям, флаги качества данных.

### 6.2 Обязательные слои

| Слой | Кандидат-источник | Лицензия (проверить) | Статус в этом проходе | Если закрыт |
|---|---|---|---|---|
| Пешеходный граф | OSM (экстракт Geofabrik «Kazakhstan» или Overpass по рамке) | ODbL | недоступен из песочницы | полевая дорисовка выборки |
| Объекты вида X | официальный реестр (управление здравоохранения/образования; data.egov.kz — проверить) | неизвестна | недоступен | OSM + оценка полноты по сверке |
| Население | GHS-POP (JRC), WorldPop, Kontur Population | по памяти CC BY 4.0 | недоступен | только районные итоги БНС |
| Районные итоги населения | БНС, динамические таблицы Шымкента | неизвестна | недоступен | — |
| Границы районов и микрорайонов | OSM `boundary=administrative`, `place=*`; акимат | ODbL / ? | недоступен | сетка H3 |
| Ограничения размещения | функциональное зонирование генплана, кадастр (свободность и категория земли), СЗЗ предприятий, водоохранные зоны, охранные зоны сетей, зоны подтопления, возможное загрязнение почв | закрыто или неизвестно | не проверено | ручной ввод участков пользователем с пометкой «не проверено» |
| Запланированные объекты | генплан, ПДП, План развития, бюджетные программы | официальные акты | не проверено | матрица статусов, раздел 4 |

### 6.3 Алгоритмический baseline (без AI)
1. Строим пешеходный граф OSM: дороги, кроме магистралей без тротуаров, плюс footway, path, steps. Магистрали без переходов становятся барьерами.
2. Центроиды ячеек населения привязываем к ближайшему узлу. Если до узла больше 200 м, ячейка получает флаг «плохая привязка» и выносится в отчёт, а не молча считается.
3. Объекты привязываем так же. Входы зданий почти наверняка неизвестны, это источник ошибки.
4. Считаем многоисточниковый Дейкстру и получаем `d_i` — сетевое расстояние до ближайшего объекта. Время = `d_i / v`, где скорость `v` — параметр (например, 3,6 / 4,5 / 5 км/ч), а не факт. Чувствительность показывать всегда.
5. Считаем метрики покрытия, раздел 6.4, по городу, району и микрорайону.
6. Для каждого участка-кандидата считаем прирост покрытия (максимальное покрытие, жадный шаг). Если известна мощность объекта, добавляем E2SFCA.
7. Строим матрицу сценариев: порог × источник населения × слой объектов × скорость. Для каждого участка выводим долю сценариев, где он первый. Это и есть «устойчивость выбора» — прямой аналог устойчивости плана в STUPITS.
8. What-if «добавить переход или тротуар» — это добавление ребра в граф и пересчёт. Это и есть интерактивное изменение инфраструктуры, только без транспортной симуляции.

### 6.4 Показатели покрытия
- `C(T) = Σ p_i·[d_i ≤ T] / Σ p_i` — доля населения в пределах T по сети.
- `U(T) = Σ p_i·[d_i > T]` — непокрытое население в людях; это главный показатель для приоритета.
- `Gap = C_район − C_микрорайон` — сколько скрывает агрегат.
- `ΔU_s(T)` — сколько ранее непокрытых жителей покрывает участок s.
- `Rank1_s` — доля сценариев, где s лучший.
- `Detour = d_сеть / d_прямая`, медиана по микрорайону — индикатор барьеров.
- `Snap_flag_share` — доля населения с плохой привязкой. Это показатель качества данных, а не результат.

### 6.5 Возможные ошибки
| Ошибка | Следствие | Как ловить |
|---|---|---|
| Прямой радиус вместо сети | завышение покрытия (в синтетике +22,5 п.п. при 500 м) | только сетевые расстояния; радиус показывать отдельно с подписью |
| «Нет в OSM» = «нет в городе» | ложные «пустыни» | основной слой — официальный реестр; сверка OSM и реестра по полноте и точности в пределах 100 м |
| Население новых массивов отсутствует в сетке (снимки и перепись старше застройки) | недооценка дефицита именно там, где проблема | сравнить с вводом жилья и контурами зданий; флаг «новая застройка» |
| Нет пешеходных путей в частном секторе и закрытых ЖК в OSM | ошибочные расстояния | полевая проверка 20–30 маршрутов |
| Близость ≠ услуга (прикрепление к ПМСП, мощность, очереди) | неверные выводы | показывать «пешую близость», а не «обеспеченность»; E2SFCA только при известной мощности |
| Краевые эффекты (объекты за границей города) | ложный дефицит у границы | буфер 2 км вокруг города при расчёте |
| Устаревшие границы районов (Туран) | неверная агрегация | версия границ с датой и актом |
| Выбор порога | смена лучшего участка (синтетика: A при 500 м → C при 800 м) | всегда несколько порогов; норматив — после проверки СП РК |

### 6.6 Роль AI
Не нужен для маршрутизации, покрытия, оптимизации и ранжирования — это детерминированный код. Полезен там, где есть неструктурированный текст:
1. Извлечение списка объектов из PDF и HTML официальных страниц в таблицу. Обязательна ручная проверка выборки и метрика точности.
2. Советник, объясняющий результат. Числа даёт код, как уже сделано в STUPITS.
3. На уровне 1–3 месяцев — классификация публичных агрегированных обращений и новостей по типу проблемы и адресу. Это для P2.

Персональные данные обращений не собирать.

### 6.7 Как измерить пользу
- Качество данных: полнота и точность OSM относительно реестра; доля плохо привязанных ячеек.
- Качество модели: 20 пар «дом — объект», сетевое расстояние сравнить с замером на месте или ручной проверкой маршрута.
- Ценность для пользователя: 3–5 целевых пользователей решают задачу «выбрать из 3 участков». Сравнить время, согласие с экспертом и то, меняет ли инструмент их исходный приоритет.

## 7. Карточка потенциального проекта

**Шаблон (поля):** название; вид объекта; проблема со ссылками на fact_id; территория (микрорайон или полигон); непокрытое население U(T) диапазоном по сценариям; участки-кандидаты (только из публичных источников, со статусом земли); ΔU по сценариям; Rank1; ограничения размещения со статусом проверки; статус в документах (раздел 4) с источниками; стоимость строительства; эксплуатационные расходы; ответственный орган; что проверить на месте; дата расчёта и версии всех слоёв.

**Стоимость:** неизвестна. Сценарный диапазон допустим только после выгрузки не менее 3 сопоставимых контрактов госзакупок или бюджетных программ с датой, регионом, мощностью и видом работ. До этого в карточке стоит `unknown`.

**Пример (SYNTHETIC, не Шымкент):** «Объект X в микрорайоне SE». U(800 м) в SE ≈ 9 443 чел. (derived: 12 793 × (1 − 0,2619)). Прирост покрытия при 800 м: C +6 584, B +5 662, A +4 937. При 500 м: A +6 852, C +5 579, B +5 157. **Вывод карточки: рекомендация неустойчива к порогу.** Нужен обоснованный норматив, без него участок выбирать нельзя.

## 11. Синтетический эксперимент (выполнен)

- **Файлы:** `A04_synthetic_experiment.py`, `A04_synthetic_results.json`.
- **Версии:** Python 3.12.3, networkx 3.6.1, numpy 2.4.4.
- **Команда:** `python3 A04_synthetic_experiment.py > A04_synthetic_results.json`.
- **Вход:** решётка улиц 2×2 км с шагом 50 м (1 600 узлов, 3 061 ребро). Барьер на y=1000–1050 с переходами только при x=400 и 1600. Закрытая промзона x 1300–1700, y 200–600. Население — гамма-распределение с seed=42 и плотностями NW 120, NE 90, SW 45, SE 35. Объекты: (500,1500), (1500,1500), (600,700). Кандидаты: A (1500,950), B (1200,150), C (1850,750).

| Порог | Покрытие по радиусу | Покрытие по сети | «Ложно покрыты» | SE по сети |
|---|---|---|---|---|
| 500 м | 67,4 % | 44,9 % | 22,5 % | 1,3 % |
| 800 м | 94,3 % | 83,3 % | 11,0 % | 26,2 % |
| 1000 м | 96,7 % | 93,8 % | 2,8 % | 53,2 % |

Коэффициент обхода (сеть / прямая): медиана 1,34, p90 1,41, максимум 1,86.

**Выводы:**
- **H1 подтверждена на игрушке.** Радиус завышает покрытие, сильнее всего — при малых порогах.
- **H2 подтверждена.** Агрегат маскирует провал.
- **H3 частично.** Порядок участков по радиусу и по сети здесь совпал, но порядок поменялся при смене порога (500 м: A>C>B; 800 м: C>B>A). Величина прироста по радиусу и по сети различалась (A при 800 м: 3 229 против 4 937).

На решётке обход завышен по сравнению с реальной сетью. Числа описывают механизм, а не масштаб в Шымкенте.

## 14. Три сильных возражения против рекомендации

1. **Близость — не доступность услуги.** Прикрепление к ПМСП, мощность, очереди и качество важнее метров. Часть жителей ездит на машине или автобусе. Пешеходная метрика может отвечать не на тот вопрос, который реально решает акимат.
2. **Мусор на входе там, где важнее всего.** Без свежего населения новых массивов и официального реестра MVP будет систематически ошибаться именно в новых территориях — главной зоне проблемы.
3. **Реальные решения о размещении определяет земля и бюджет, а не покрытие.** Свободного участка может просто не быть. Инструмент рискует оптимизировать то, что не выбирают, а жюри GovTech может ожидать больше AI, чем здесь честно нужно.
