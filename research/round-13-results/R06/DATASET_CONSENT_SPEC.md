# R06 · Спецификация: будущий датасет сообщений жителей (согласие и минимизация)

Статус: ПРОЕКТ спецификации, round 13. Ничего из описанного ниже **не реализовано и не включено**.
Сейчас R06 не экспортирует сообщения ни в Git, ни в обучение моделей, ни во внешние сервисы
(проверка: `tests/civic/R06/test_r06_r13_frontend.py::test_no_automatic_export_of_messages`).
Модель R08 обучена только на синтетическом корпусе (`training_data_status =
synthetic_demo_only;real_data_NOT_EVALUATED`), поэтому каждая её подсказка требует проверки сотрудником.

## 2. Условия, без которых датасет не собирается

1. **Отдельное согласие.** Согласие на публикацию (`consent_public`) — НЕ согласие на обучение. Нужен
   отдельный, необязательный и не отмеченный заранее пункт формы: «Разрешаю использовать обезличенный
   текст для улучшения подсказок категорий». Отказ не влияет на приём сообщения.
2. **Отзыв.** Отзыв по номеру квитанции исключает текст из всех будущих выгрузок; уже обученные
   версии модели помечаются как содержащие отозванные записи и переобучаются в следующем цикле.
3. **Правовая основа.** До запуска — оценка юристом по Закону РК «О персональных данных и их защите»
   (№ 94-V) и внутреннему положению оператора платформы; без этой оценки выгрузка запрещена.
4. **Решение человека.** Каждая выгрузка запускается вручную ответственным лицом, с записью в журнале
   (кто, когда, сколько записей, хэш набора). Автоматического экспорта по расписанию нет.

## 3. Минимизация (что попадает в набор)

- Берутся только записи с отдельным согласием, не отозванные, старше 30 дней (время на отзыв).
- Поля: `text` после обезличивания, `language`, итоговая категория сотрудника
  (`staff_category` либо `category`), отметка «категорию проверил сотрудник».
- НЕ берутся: `client_hash`, `client_request_id`, `receipt_id`, `public_id`, координаты точнее
  района, `object_id`, даты точнее месяца, ответы и заметки сотрудников, имена сотрудников, решения
  модерации, подсказка модели (чтобы не учиться на своих же ошибках).
- Обезличивание: автоматическая замена (телефоны, ИИН, e-mail, ссылки, длинные номера — правила
  `ui/civic_feedback/text.py`) **плюс** ручная проверка каждого текста: регулярные выражения не находят
  имена, адреса и описания людей. Текст, который нельзя обезличить без потери смысла, исключается.
- Минимальный размер группы: категории и языки, где меньше 20 записей, в выгрузку не попадают.

## 4. Синтетика и проверка

- Тесты, демонстрации и фикстуры — только синтетические тексты с пометкой (как сейчас:
  `ui/civic_feedback/fixtures.py`, корпус R08 `corpus_synthetic_v2.jsonl`). Реальные сообщения в Git,
  тестах, скриншотах и отчётах не используются.
- Перед заменой синтетической модели на обученную на реальных данных: оценка на отложенной
  выборке, проверенной двумя сотрудниками независимо; отчёт по качеству по языкам (ru/kk) и
  категориям; новый `training_data_status` и `score_kind`. Пока score не откалиброван на реальных
  сообщениях, R06 его не показывает (`CALIBRATED_SCORE_KINDS` пуст).
- Даже после этого подсказка остаётся подсказкой: категорию жителя она не меняет, решение — за
  сотрудником.

## 5. Хранение набора

- Вне Git и вне общего хранилища кода; доступ — поимённый список; шифрование на диске.
- Срок хранения набора — до следующего обучения, но не более 12 месяцев; затем удаление с записью.
- Каждая версия модели ссылается на хэш набора, а не на сами тексты.

3. Ручной инструмент обезличивания и журнал выгрузок (R06 + R08).
4. Протокол оценки модели на реальных данных (R08).
