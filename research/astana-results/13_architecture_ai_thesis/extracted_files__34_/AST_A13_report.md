|---|---|---|---|---|
| `astana_hackathon` | замороженная учебная модель ТЗ с эталонами | `data/city_data.json`, `events.json`, hash `0cda24ae15a0` | разрешён, с меткой «учебная» | существует как код; конфигурация проверена прототипом E7 |

| `shymkent_real` | своя аналитика Шымкента | то же; первый проход тоже не получил данных (A13-F015 — гипотеза) | запрещён | контракт |

Общие сущности: City, Source, DataVersion и GeographyVersion, IndicatorDefinition, Observation, DomainModel, Scenario, ComputedResult, Evidence, Explanation. Новое по сравнению с первым проходом — `IndicatorDefinition` как ключ сопоставимости:

```json
{"indicator_definition": {"id":"pm25_annual_mean@kazhydromet-v1", "name_ru":"…", "name_kk":"…",
  "unit":"мкг/м³", "direction":"lower_is_better", "geography_level":"city|district|station",
  "method":"…", "method_version":"v1", "source_ids":[], "valid_from":null, "valid_to":null}}
```

**Правило сравнения городов.** Значения Астаны и Шымкента сравниваются только при совпадении трёх условий:
- `indicator_definition.id` вместе с `method_version`;
- `geography_level`;
- пересекающийся `period`.

Иначе API возвращает `comparison_status: "incompatible"` с причиной. Одинаковое название показателя не означает сопоставимости.

## 3. Контракты, хранение, старые запросы, воспроизводимость

**API.**
- `/api/v2/{config}/…`, где `config ∈ {astana_hackathon, astana_real, shymkent_real}`.
- Старые `/api/*` без поля города — алиас `astana_hackathon`. Прототип E7 показал побайтное совпадение канонического JSON.
- Ответ любой операции: `result_id` (sha256 от конфигурации, data_version, операции, тела запроса и версии движка), `data_version`, `mode`, `label`, `outputs`, `evidence_refs`.

**Контроль старых запросов.**
1. Golden-снимки канонического JSON для контрольного сценария. Пример: simulate для плана ТЗ, sha256 `ff3b5e86…6d257`.
2. CI сравнивает снимки при каждом изменении.
3. Тело запроса без `city` никогда не попадает в real-конфигурацию.

**Хранение по требованиям.**
- Сейчас: JSON и GeoJSON в git с хэшем версии. Объём учебной модели и первых наблюдений — единицы мегабайт.
- Появились ряды по годам, несколько версий границ, данные двух городов: один файл DuckDB или SQLite плюс GeoParquet.
- Нужна правка несколькими людьми или пространственные запросы на сервере: PostGIS.

Порог перехода — не «потому что так принято», а появление конкретной операции, которую файлы не выдерживают.

**Воспроизводимость.**
- Фиксированные версии в `requirements-lock.txt` (есть в репозитории).
- В каждом ответе указаны `data_version` и версия движка.
- Seed у любых стохастических анализов (как в E6).

**Миграция без переписывания UI.**
1. Сервер добавляет в `bootstrap` поля `config`, `mode`, `label`, `indicator_definitions`.
2. UI показывает бейдж режима.
3. Карта берёт домен и направление из `indicator_definitions`.
4. Переключатель конфигурации добавляется последним.

## 4. Эксперименты этого прохода

Среда: Python 3.12.3, numpy 2.4.4, коммит `834a25f`. Скрипты и результаты приложены.

**E5. Казахские числительные и фильтр советника** (`kk_numeral_filter.py`). Двенадцать синтетических предложений, вызов `agent.evidence.qualitative_comment`.

| Язык | Предложений с числовым утверждением | Пропущено фильтром | Ложных удалений |
|---|---|---|---|
| ru | 4 | 1 («десятки процентов») | 0 |
| kk | 6 | **4** («бес», «он екі», «үш», «жартысын») | 0 |

Цифры «5» и слово «миллион» удаляются. Вывод: фильтр рассчитан на русский. Для двуязычного советника нужен казахский словарь числительных и долей. Сам тест годится как регрессионный набор.

**E6. Устойчивость ранжирования** (`rank_sensitivity.py`). Модель `astana_hackathon`, возмущения синтетические и не откалиброваны: веса умножаются на LogNormal(0, σ) с нормировкой, каждый эффект — на U(1−a, 1+a). На каждый уровень 60 выборок, всего 94.7 с.

| σ = a | Базовый топ-1 остаётся топ-1 | Базовый топ-1 в топ-10 | Разных топ-1 | Пересечение топ-10 | Регрет базового топ-1: медиана / p95 |
|---|---|---|---|---|---|
| 0.1 | 43 % | 100 % | 6 | 7.8 из 10 | 0.01 / 0.10 |
| 0.2 | 28 % | 83 % | 16 | 5.3 | 0.065 / 0.30 |
| 0.3 | 20 % | 67 % | 23 | 3.4 | 0.125 / 1.00 |

Базовый план во всех трёх уровнях остаётся самым частым победителем. Интерпретация (derived): в учебной модели «лучший план» — хрупкая точка внутри плато почти равных планов. Для `astana_real`, где неопределённость эффектов заведомо больше, разумно показывать множество планов в пределах ε от оптимума и частоту их «победы».

Ограничения: 60 выборок дают широкий доверительный интервал (±≈12 п.п. для долей). Диапазоны возмущений — предположение.

**E7. Прототип конфигураций** (`cityconf_proto.py`). Изолированный модуль вне репозитория.
- Эталоны воспроизведены: `references_ok: true`.
- `legacy_byte_identical: true`.
- `result_id` детерминирован.
- `astana_real` и `shymkent_real` получили отказ «композитный индекс не определён… показывайте наблюдения по отдельности».

Код движка не менялся. Это подтверждает, что двухгородная конфигурация надстраивается над движком, а не требует его переписывания (observed для учебной модели; для real нужна новая модель).

## 5. AI-функции

Общие правила для всех функций:
- город и период — обязательные параметры запроса;
- числа дают только инструменты;
- каждое извлечённое число имеет `source_ref` и `locator`;
- при недостатке сведений — явный отказ с перечнем недостающего;
- текст найденных документов — недоверенные данные: модель не исполняет инструкции из них, а инструменты вызывает только по запросу пользователя (Greshake et al. 2023, AST-A13-L08).

| Функция | Пользователь и решение | Baseline без LLM | Инструменты и проверка чисел | Метрики | Отказ |
|---|---|---|---|---|---|
| F1. Поиск по официальным документам с цитатами (ru/kk) | Аналитик проверяет, какая норма или программа действует в Астане на дату | BM25 по корпусу с полями `city`, `valid_from/to`, `lang` | Ответ = фрагменты с URL и редакцией; утверждение без фрагмента удаляется (подход ALCE, L07) | recall@5, citation precision и recall на отложенных вопросах ru и kk отдельно | нет фрагмента нужного города или периода — «не найдено», а не пересказ |
| F2. Извлечение наблюдений из таблиц и отчётов | Разработчик наполняет `astana_real` | Парсер XLSX/CSV и ручной ввод | Каждое значение — Observation с `locator`; LLM только предлагает, человек подтверждает | точность по полям (значение, единица, период, география) на двойной ручной разметке | неясны единица или территория (город, область, агломерация) — поле `null` и вопрос |
| F3. Поручение → ограничения (ru/kk) | Сотрудник формулирует условия для сравнения вариантов | Форма и словарный парсер (A13-F014) | JSON Schema и валидатор движка | exact, slot-F1, регрет, корректный отказ на невыполнимых; ru и kk раздельно | двусмысленность — один уточняющий вопрос |
| F4. Объяснение результата | Любой пользователь читает разбор | Шаблон `agent/offline.py` | Отчёт собирает код; комментарий LLM проходит фильтр чисел ru и **kk** (E5) | доля непроверяемых утверждений до фильтра; слепая оценка против шаблона | нет результата инструмента — объяснения нет |

Где AI не нужен: оптимизация, расчёт показателей, сравнение городов. Это код. Точность AI-функций не обещаю: метрики выше определяют эксперимент, а не результат.

**Поправка к первому проходу.**
- A13-L012 (OptiMUS) верен как v0.2; у работы есть версии v0.1 и v0.3.
- Кандидаты из памяти Malczewski 2006, Geertman & Stillwell 2004, Vonk et al. 2005, Lempert et al. 2003 **по-прежнему не подтверждены**. Литература по GIS-MCDA и системам поддержки планирования — главный пробел.

**Т1. Перевод поручений в валидируемые ограничения на двух языках.**
- Гипотеза: LLM со схемой и валидатором даёт меньший регрет решения, чем словарный парсер, на отложенных ru- и kk-поручениях. Разрыв на kk больше, чем на ru. Это нужно проверить, а не утверждать.
- Baseline: парсер из A13-E4 и форма.
- Настройка и проверка: промпты и словарь настраиваются на ru-части набора авторов A; замораживаются; проверка на наборе авторов B (ru и kk), который разработчик не видел.
- Метрики: exact, slot-F1, регрет, корректный отказ.
- Сопоставимость: каталоги мер городов разные, поэтому сравнивается тип ошибки, а не абсолютный балл.
- Пригодность для одного разработчика: высокая.

**Т2. Устойчивость рекомендаций портфеля мер: точка против множества почти-оптимальных планов.**
- Гипотеза: доля смены топ-1 при реалистичной неопределённости высока (пилот E6: 57–80 %), а множество в пределах ε стабильно. Показ множества с частотой побед снижает регрет пользователя по сравнению с показом топ-1.
- Методы: L01–L05 (RDM, анализ чувствительности).
- Протокол: Sobol или Morris через SALib по весам и эффектам; критерии max-E, minimax, min-regret; затем небольшое пользовательское исследование с выбором плана при двух интерфейсах.
- Ограничения: без калибровки выводы методические.
- Пригодность: высокая; пилот уже выполнен.

**Т3. Перенос метода расчёта показателя доступности между Астаной и Шымкентом.**
- Гипотеза: процедура «OSM-объекты, сеть (OSMnx, L06), доля населения в радиусе», настроенная на Астане и замороженная, даёт на Шымкенте согласие с официальными районными данными (ранговая корреляция по районам) не хуже, чем на Астане.
- Настройка: Астана (теги, радиусы, дедупликация).
- Проверка: Шымкент как отложенный город, без перенастройки.
- Метрики: Spearman по районам против официальных количеств объектов, полнота OSM по выборочной ручной проверке, разница метрик между городами.
- Ограничения сопоставимости: при 5–6 районах на город корреляция статистически слаба; полнота OSM сама различается между городами; нужны совпадающие период и определение объекта. Два города не доказывают универсальность: результат формулируется как «перенос на один отложенный город».
- Данные: официальные количества школ и поликлиник по районам (не проверены, зависимость от A01–A12).
- Пригодность: средняя; зависит от данных.

5. Получить по одной официальной таблице на город из среды без блокировок. Без этого `astana_real` и `shymkent_real` остаются пустыми.

## 11. Три сильных возражения

1. **Нет реальных данных — нет реального продукта.** Весь проход опирается на учебную модель и инфраструктуру. Возможно, сначала нужно доказать, что данные вообще существуют на районном уровне, а архитектуру строить потом.
2. **E6 доказывает свойство синтетической модели, а не Астаны.** Хрупкость топ-1 может быть артефактом плоской учебной формулы. В реальной модели плато может быть уже или шире.
3. **Т3 статистически слаба.** 5–6 районов на город и разная полнота OSM могут не позволить отличить «метод переносится» от «повезло». Возможно, нужна более мелкая география, а её официальная доступность не установлена.
