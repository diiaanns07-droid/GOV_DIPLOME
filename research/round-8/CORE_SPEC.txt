city-plan-v2: ПЛАНИРОВАНИЕ НЕСКОЛЬКИХ СОЦОБЪЕКТОВ
Цель: пользователь задаёт варианты размещения школ ИЛИ поликлиник, условные стоимости и бюджет; сравнивает допустимые наборы и три оптимальных плана. Полезность измеряется только геометрическими расстояниями до выбранных контрольных точек в данном срезе.

ОБЛАСТЬ
Один город и одна категория на сценарий (school/outpatient_clinic), исходный bbox. Контрольных точек 1..25, кандидатных объектов 0..16, выбрать можно 0..max_selected (целое 0..5). Оригинальные записи не удалять/не изменять; кандидат kind=hypothetical. Каждый кандидат: id, lon, lat, category, kind, cost (целое 1..1000000 условных единиц). Бюджет 0..1000000. Стоимости задаёт пользователь/явно synthetic demo, не реальные тенге и не смета.
Контрольная точка: id,lon,lat,weight (целое 1..100, default 1 при создании). Вес — пользовательский приоритет, не численность жителей.
coverage_radius_m — целое 100..5000; параметр анализа, НЕ норматив пешей доступности. Всё по прямой в пределах среза, без пешего времени, населения/мощности/трафика и прогноза социальной пользы.
required_ids/excluded_ids — уникальные candidate IDs без пересечения; required включены, excluded исключены. Если budget/count делают required невыполнимыми, вернуть infeasible с причиной, не убирать ограничения молча.
При смене города/категории сценарий явно сбрасывается, старый ответ worker/объяснения не применяется.

ФОРМАТ ВХОДА
schema_version="city-plan-v2"; city_id; source_snapshot; category; control_points; candidates; budget; max_selected; coverage_radius_m; required_ids; excluded_ids; selected_ids (ручной план).
ID не длиннее 64 символов, уникальны внутри каждого массива; ссылки только на существующих кандидатов; source и proposed ID различать kind/namespace в ответе.
Strict JSON ≤256 KiB, запрет дубликатов ключей, NaN/Infinity/1e999, плохих координат/чужого bbox/snapshot/города, неожиданных полей кроме явно разрешённого derived_results. Импорт пересчитывает результаты, не доверяет derived_results; при отказе состояние неизменно. Никаких URL-загрузок или кода из сценария. Строки отображать как текст.
v1 city-whatif-v1 продолжает работать без изменений. При явном переносе v1→v2 пользователь должен задать стоимости и бюджет; не придумывать реальные цены. Допустимо сохранить режимы раздельными, без миграции в MVP.

РАСЧЁТ
Расстояние — гаверсинус R=6371008.8, вход [lon,lat], clamp промежуточного в [0,1].
Для оптимизации каждое расстояние один раз округлить до целых миллиметров Math.round(d_m*1000) (для Python floor(x+0.5), все значения неотрицательны); это metric_version="haversine-mm-v1".
Это делает лексикографические сравнения детерминированными. UI может показывать метры, но должен считать delta из неокруглённых до метров мм.
Для каждого control point: nearest baseline среди исходных записей категории; nearest after среди baseline и выбранных кандидатов. При пустом наборе объектов distance=null, а не 0. Ничьи разрешать стабильным source/hypothetical key; порядок входных массивов не должен менять план.
Все before/after относятся к записям среза. Если before=null, delta=null даже при известном after.
Метрики плана:
unknown_count = количество точек без определённого after;
weighted_sum_mm = сумма weight*after_mm по известным; weighted_mean_mm = weighted_sum_mm/сумма weight всех точек только если unknown_count=0, иначе null;
max_mm = максимум after_mm только если все известны, иначе null;
covered_weight = сумма весов точек с известным after_mm <= coverage_radius_m*1000;
coverage_fraction=covered_weight/sумма всех весов (охват выбранных точек, не жителей);
cost=sum выбранных candidate.cost.
Если baseline пустой, покрытие 0 в данном наборе записей не доказывает отсутствие услуги в городе. UI явно различает это.

ТОЧНЫЙ ПОИСК
Полный перебор подмножеств до 16 кандидатов (<=65536) с budget/max_selected/required/excluded. Расстояния к источникам и кандидатам предвычислить; не считать гаверсинус внутри каждого шага перебора. Включить пустой план, когда допустим.
Три победителя по лексикографическим ключам (меньше лучше):
1 mean: unknown_count, weighted_sum_mm, max_mm, cost, sorted IDs;
2 minimax: unknown_count, max_mm, weighted_sum_mm, cost, sorted IDs;
3 coverage: -covered_weight, unknown_count, weighted_sum_mm, max_mm, cost, sorted IDs.
Для ранжирования неопределённый max трактовать как infinity внутри алгоритма, но наружу strict JSON с null. weighted_sum по частично известным никогда не сравнивать раньше unknown_count.
При равных числах sorted IDs лексикографически, массивы сравнивать по элементам, более короткий префикс раньше. Ограничение 16 нельзя незаметно обойти эвристикой с подписью «точный оптимум».
Оптимум только среди введённых кандидатных мест/условий, не лучший план города.
Парето для известной полной геометрии: (cost, weighted_sum_mm) минимизировать; доминирование <= по двум и строго < по одному. Равные пары свернуть детерминированно к одному представителю. Если есть unknown, не строить сопоставимую точку из partial sum.
Чувствительность минимум: бюджеты [0, floor(B/2), B] без дублей; неизменные кандидаты/веса/constraints. infeasible честно отмечать; не обещать снижение реальных расходов. Дополнительная проверка весов/радиуса — исследование параметров, не вероятностная устойчивость города.

ИНТЕРФЕЙС МОДУЛЕЙ (JS, JSON-compatible; названия можно реализовать адаптером)
validatePlanScenario(input, context) -> validated scenario или typed error
context содержит актуальный city/bbox/source_snapshot/исходные записи и версии.
evaluatePlan(context, scenario, selectedIds) -> rows + metrics + feasibility
optimizePlans(context, scenario, options?) -> {status, objectives:{mean,minimax,coverage}, pareto, evaluated, feasible_count, problem_digest, metric_version}
Digest покрывает source_snapshot, город, категорию, полный problem input (точки/веса, кандидаты/стоимости, бюджет/ограничения, radius, версии), не зависит от порядка массивов. selected_ids учитывать в digest ручного сценария, но не в problem_digest неизменной оптимизационной задачи.
UI не блокируется: Web Worker или ограниченные чанки с event loop. Cancel и request_id/problem_digest защищают от старого результата. Если поиск прерван/неполон, не ставить status=optimal.
Node-тесты должны иметь headless путь без DOM; Python-оракул независимый, не трансляция JS.

ВЫХОД ДЛЯ ПОЛЬЗОВАТЕЛЯ
Карта/список кандидатов с cost, ручной набор, сравнение «текущий / среднее / худшая точка / охват», таблица по точкам, Парето стоимость→расстояние и изменение бюджета. Можно осмысленно сравнить одинаковые планы без создания видимости трёх разных решений.
Результат поиска только предложение; пользователь нажимает «Применить». Отмена/очистка возвращает ручное состояние, не меняет исходные записи.
Видимые source/QA/hypothetical/условный бюджет. Объяснение кодом по вычисленным фактам: почему разные планы, чем жертвуем, почему нельзя сделать вывод о вместимости.
