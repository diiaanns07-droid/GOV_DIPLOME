ТВОЯ РОЛЬ: R02 — БАЗА ГОРОДСКИХ ОБЪЕКТОВ, API И ДОСТУП РЕДАКТОРА
Цель: реальное серверное хранение и контролируемая публикация объектов. Редактор меняет срок, а публичная история и данные остаются после перезапуска.

ГРАНИЦА
Пиши ui/civic_store/, tests/civic/R02/ и свои results/handoff. Общий ui/web_server.py не редактировать: дай R01 минимальные инструкции адаптера/patch в results. Без тяжёлой смены web-framework, Node backend, Docker-only запуска. SQLite/стандартные библиотеки подходят первому локальному пилоту; решение о расширении зависимостей передай R01.
Прочитай существующие Handler/create_server и защиту запросов. Не переносить секреты из .env. На исходной версии civic API пока нет.

ПЛАН ДО 300 МИНУТ
00–25: разложи контракт civic-v1 на таблицы, публичные DTO и состояния. Первый маленький результат: миграция/схема + независимый тест чтения пустой базы в tmp-dir + handoff и push.
25–75: repository/service CRUD. Параметризованный SQL, ограничения дат/геометрии/денег, список/деталь, серверные IDs/revision/updated_at. Отдельные draft/published/archived. Тесты restart и исходного источника. Не считать отсутствие записи пустым успешным объектом.
75–135: обновление и публикация в транзакции вместе с audit history. optimistic concurrency expected_revision, 409 при гонке. При изменении публичного срока обязательная причина; original_planned_end после первой публикации сохраняется. rollback не оставляет половину истории.
135–195: локальная учётная запись редактора через CLI с getpass, хэши пароля через стандартный password KDF, session lifecycle, logout, HttpOnly/SameSite и Secure по HTTPS. CSRF + same-origin/Host; настройки безопасны по умолчанию. Ограниченный повтор логина, не выводить пароль/session в логи. Никакого hardcoded admin/admin.
195–255: полный CivicService.handle и resolve_principal, allowlist публичных полей, пагинация/фильтры, идемпотентный импорт civic пакета R05 с dry-run и отчётом. Новый импорт создаёт draft и не затаптывает ручные опубликованные изменения. Проверь доступ к DB в multithread HTTP-окружении, блокировки/transactions/busy timeout и корректное закрытие.
255–300: интеграционный пример адаптера для R01, реальные запросы через временный тестовый сервер, документы первого запуска и восстановления. Риски/пределы локального auth сообщить прямо. Последний checkpoint включает small safe demo dataset, результаты тестов, DELIVERY.json.

Runtime .sqlite/.wal/.shm не лежат в web/ и не попадают в Git.

СОХРАНЯТЬ ЧАСТО — ОБЯЗАТЕЛЬНО
После первого полезного результата, каждого небольшого законченного этапа и перед остановкой:
сохранить файлы -> обновить свой STATUS.md -> проверить diff/секреты -> git add только перечисленных собственных путей -> commit -> push своей выделенной ветки.
Ориентир: checkpoint каждые 25–40 минут, обычно 6–10 содержательных сохранений за длинную сессию. Не делать пустые коммиты ради счётчика. Перед длительным обучением, установкой, скачиванием, браузерным прогоном или сменой контекста сначала push.
В handoff: DONE/PARTIAL, что проверено, команды/результаты, что не запускалось, следующий один шаг. Текущий SHA и статус push сообщай после команды; не редактируй бесконечно файл ради SHA его собственного коммита.
Ошибка push != сохранение в GitHub. Зафиксируй ошибку; при отсутствии upstream настрой только свою ветку. После двух одинаковых сетевых ошибок не трать всю сессию на повторы: продолжай локально и оставь точное восстановление. Не меняй credentials, доступы, remote и не делай force push.
Не git add .; не коммитить .env, ключи, cookies, SQLite с пользователями, private обращения, кэш, venv, node_modules, гигантские веса и ZIP. Собственные новые артефакты должны быть доступны как обычные файлы Git; большие воспроизводимые результаты — манифест + скрипт + допустимая лицензия.

ДОКАЗАТЕЛЬСТВА
Отчёт агента — материал, не истина. Импортированные скрипты прочитать до запуска.
Сохранять город, исходный URL, дату доступа/публикации, период, лицензию и статус observed/derived/hypothesis/synthetic. Старое объявление о перекрытии не означает действующее перекрытие.
Нельзя: синтетические жители как реальные; бюджет учебной модели как тенге; unknown как 0; школьный граф как проверенная автомобильная сеть; шаблон как ответ LLM; недоступный сайт как доказательство отсутствия данных.
При внешнем 403/timeout сохранить конкретный доступный результат и ограничения, перейти на существующие проверенные файлы/fixtures. Не изобретать новые факты и не обходить ограничения доступа.
Проверки указывать PASS/FAIL/NOT_RUN с причиной, входами и SHA кода. Скриншот должен быть реальным, а не сгенерированным. Недоступная подложка не подтверждает работу 3D.
Качество важнее объёма: meaningful tests на риски, а не тысячи повторяющихся assert для числа в отчёте.
