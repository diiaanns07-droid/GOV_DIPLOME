# Протокол T3 (K09, раунд 9): обычный (nominal) против устойчивого (robust) плана при условном исключении исходных записей

**Предрегистрация.** Этот файл, `config/t3_config.json` и `config/t3_attribute_sets.json` зафиксированы коммитом **до** прогона эксперимента. Seeds 0–9, правила и метрики заданы заранее, отбор seeds под результат запрещён. До фиксации выполнен только прогон формата на 12 задачах в scratch: проверялись столбцы, выводы не смотрелись.

T1 (r3) и эксперимент r8 не меняются. T3 — отдельный протокол.

## Вопрос

Насколько часто и насколько сильно устойчивый план (минимум худшего вектора потерь по случаям) отличается от обычного оптимального плана (mean-оптимум на полном срезе)? Какой ценой в среднем расстоянии на base это достигается? Зависимость смотрим от числа и типа случаев исключения, размера задачи и бюджета.

Вывод касается **метода** (свойств устойчивой постановки на фиксированных синтетических задачах). Это **не** вероятность кризисов, закрытий или рисков в городе.

## Постановка

Постановка соответствует CORE_SPEC r9.

**Входы:**
- envelope `city-resilience-v1` = полный city-plan-v2 плюс 1..7 пользовательских случаев;
- случай `base` (без исключений) добавляется автоматически.

**Расчёт по случаям:**
- В каждом случае baseline — только исходные записи, не входящие в `disabled_source_ids`.
- Кандидаты, бюджет и ограничения одинаковы во всех случаях.
- Потери плана в случае: **L** = (unknown_count, weighted_sum_mm, max_mm); max = null считается +∞ только внутри сравнения.
- **W** — лексикографический максимум L по всем случаям, включая base. **worst_case_ids** — все случаи с L = W.

**Планы:**
- **nominal** = минимум (L_base, cost, sorted ids). Это mean-цель v2 на base.
- **robust** = минимум (W, L_base, cost, sorted ids).

**Цена устойчивости** = (mean_base(robust) − mean_base(nominal)) / 1000 м. Считается, только если оба плана optimal и на base нет unknown; иначе null с причиной.

**Перебор** — полный, по ≤ 4096 подмножеств (≤ 12 кандидатов). Оракул — `k09res/resilience.py`: независимый Python, переиспользует проверенную в r8 и на этапе 1 геометрию haversine-mm-v1.

## Факторы (основная сетка)

| Фактор | Уровни |
|---|---|
| Срез | shymkent_school, astana_clinic |
| Размер | S (4 кандидата, 5 точек), M (8, 15), L (12, 25) |
| Бюджет | 0.5 и 1.0 × сумма 3 самых дорогих кандидатов; 1.0 — бюджет не ограничивает |
| max_selected, радиус | 3; 300 м |
| Семейство исключений, k | single, pair, cluster с k = 1, 3, 7; attribute (k по данным); all_disabled (k = 1) |
| Seeds | 0–9 |

Геометрия задаётся только (город, категория, seed) и вложена по размеру (первые n точек и кандидатов). Поэтому сравнения семейств, k, бюджетов и размеров на одном seed **парные**. Исключения не зависят от размера и бюджета.

## Семейства исключений (правила до прогона)

- **single** — k случаев, каждый исключает одну запись; разные случаи исключают разные записи.
- **pair** — k случаев по 2 случайные записи.
- **cluster** — k случаев по 3 записи, ближайшие к случайной якорной точке в bbox. Исключение пространственно связано.
- **attribute** — детерминированные случаи по атрибутам записей (`config/t3_attribute_sets.json`):
  - low_confidence — Overture confidence < 0.5: shymkent 6 записей, astana 7;
  - qa_flagged — QA-метки BUILD: shymkent 7, astana 0;
  - low_or_qa — объединение.

  Пустые и совпадающие наборы не включаются, поэтому в shymkent 3 случая, в astana 1. QA-метка и низкая confidence **не доказывают** ошибку записи.
- **all_disabled** — один случай исключает все записи категории. Это крайний случай: baseline пуст, проверка unknown.

## Метрики (до прогона)

1. **same_plan** — доля задач, где robust = nominal; Wilson 95%.
2. **Цена устойчивости, м:**
   - число определённых и null (с причиной);
   - доля нулей;
   - p50, p90 и max (nearest-rank);
   - медиана среди положительных.
3. **Худший вектор:**
   - класс улучшения W: none, unknown, wsum или max;
   - выигрыш в худшем случае по среднему: (W_nominal.wsum − W_robust.wsum) / сумма весов / 1000 м;
   - выигрыш по max — только при unknown = 0 у обоих.
4. **unknown отдельно** — сколько задач с W.unknown > 0 у nominal и у robust.
5. **worst_case_ids** — входит ли base в худшие случаи.
6. **Время** — оракул (предвычисление + перебор), минимум из 3 повторов; окружение фиксируется. Время BUILD — отдельно, если он есть.
7. **Срезы и контрасты:**
   - по семейству, k, размеру, бюджету, срезу; семейство × k; семейство × срез;
   - парные контрасты same_plan: k = 1 против k = 7 и бюджет 0.5 против 1.0 (точный McNemar, log10 p).

**Инварианты** проверяются утверждением (assert) в каждой задаче:
- W(robust) ≤ W(nominal);
- L_base(nominal) ≤ L_base(robust);
- отсюда цена ≥ 0 там, где она определена.

## Интеграция

Если BUILD r9 опубликует `resilience.js` с явным SHA, те же 1340 envelope прогоняются через адаптер BUILD (`run_t3.py --emit-envelopes`). Сравниваются математические результаты:
- nominal и robust ids;
- W и worst_case_ids;
- цена устойчивости;
- статусы.

Ожидания не подгоняются под ответ BUILD. Различаются ошибки адаптера, спецификации и продукта. Если BUILD r9 нет, интеграция помечается **NOT_RUN**.

## Ограничения интерпретации

- Частоты по synthetic задачам — не вероятности городских событий.
- Исключение записи — допущение о данных, а не подтверждение закрытия. Пустой baseline не означает отсутствие услуги в городе.
- Оптимум ищется только среди введённых кандидатов. Расстояния — по прямой. Стоимости — условные единицы.
- Срезы — малые bbox. Выводы касаются метода на этих срезах, а не городов.
