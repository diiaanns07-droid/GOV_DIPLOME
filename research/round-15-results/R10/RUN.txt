R10 · раунд 15 · приёмка — как запустить проверки и что они дают

Ветка R10: claude/zen-wozniak-69d41q (ветка сессии; find_branches.py --role R10). Свои пути: tests/civic/R10/, tests/e2e/,
research/round-15-results/R10/, research/handoffs/astana/R10/round15/STATUS.md.
Нужно: Python 3.11+ с pytest, Node 20+, Playwright + Chromium (NODE_PATH="$(npm root -g)"; в облаке Chromium уже есть —
«playwright install» не запускать), ffmpeg — только для .mp4 ролика. Windows: PYTHON=<сборка>\.venv\Scripts\python.exe.
Все проверки сами поднимают сервер сборки на свободном порту с ВРЕМЕННОЙ базой (init → seed-demo → seed-r14-demo →
сотрудник r10-operator; CIVIC_DEMO=1, для раунда 15 — ещё CIVIC_DEMO_WORLD=1) и ничего не пишут в репозиторий.
Браузерные проверки запускать ПО ОДНОЙ (несколько Chromium сразу на облачной машине дают ложные таймауты).
Сборку удобно держать отдельным worktree:  git worktree add --detach ../b1 <SHA сборки из BUILD.json R01>

=====================================================================================================
0. Всё сразу на одной сборке R01 (B1 / B2 / FINAL-5) — ~1 ч, вердикт «можно показывать: да / нет»
=====================================================================================================
    REF_HTML=<эталон A .html> bash tests/e2e/acceptance_r15.sh <сборка> <папка> "B1 <sha>" [--video] [--quick]
    python3 tests/e2e/save_run.py <папка> research/round-15-results/R10/<b1-sha>     # отчёты + кадры FAIL в репозиторий
  Шаги по порядку: pytest → api → numbers → e2e (часть 1, --world) → v2 (сцены 7–9) → map → perf → audit (без --quick)
  → ref (эталон, не хуже FINAL-4) → video (с --video). Итог: <папка>/ACCEPTANCE.md и VERDICT.json (tests/e2e/summary_r15.py).
  «Можно показывать: нет», если: функциональный шаг части 1 или сцен 7–9 FAIL, числа (кроме C5 — «смотреть») FAIL, русские
  подписи на ҚАЗ или ключи перевода на экране, нарушение П1, «Хроника» не доигрывает, жёсткие правила API (доступ, 5xx);
  на FINAL-5 ещё — NOT_RUN в сценах и числах. Качество вида (шрифт, зоны нажатия, контраст, термины), эталон A,
  производительность и аудит — «смотреть» со ссылкой на BUGS.

5. Визуальный контроль и производительность
=====================================================================================================
    NODE_PATH="$(npm root -g)" node tests/e2e/visual_audit.cjs --root <сборка> --out <папка>/audit [--only yard,agencies-board]
  Аудит новых экранов по VISUAL_BRIEF §4: шрифт ≥ 13 px и не больше 3 размеров, зоны ≥ 44 px, видимый фокус, контраст,
  прокрутка вбок на 375, ключи перевода, казахский не обрезан, «нет связи» → «Повторить» (1366 × ru/kk × 3 размера).
  Итог: AUDIT.md (по экранам и владельцам), AUDIT.json, кадры. WARN — правило брифа, которое приёмку не валит.
    NODE_PATH="$(npm root -g)" node tests/e2e/perf_check.cjs --root <сборка> --out <папка>/perf --repeat 3
  Первый значок карты (≤ 3 с), «Хроника» R07 и перемещение карты при 1000 целей (к/с), время ответа «Спросить Birge»
  (первый вопрос после старта и следующие).
    NODE_PATH="$(npm root -g)" node tests/e2e/map_baseline.cjs --root <сборка> --out <папка>/map --repeat 3   # первый значок, API
    NODE_PATH="$(npm root -g)" node tests/e2e/reference_check.cjs ...   # эталон A (см. tests/e2e/README.md)
    NODE_PATH="$(npm root -g)" node tests/e2e/glass_check.cjs --root <сборка> --out <папка>/glass --fps-only   # FPS (ноутбук)
  В облаке WebGL программный (3–7 к/с) — FPS хроники и перемещения мерить на ноутбуке (LOCAL), в облаке — только ИНФО.

Что можно сделать с результатами: BUGS.md — дефекты с владельцем, шагом и кадром; DELIVERY.json — итог «можно
показывать: да / нет» на каждой сборке R01 (B1, B2, FINAL-5).
