# ml/civic_forecast — прогноз проблемных территорий (R13, прототип)

Задача Gton «Предиктивная аналитика проблем региона»: ежемесячно назвать 10–30 территорий, где в следующем месяце
вероятна проблема; цель — 60–70 % прогнозов подтверждаются. Здесь — **честный прототип**: рабочий конвейер и методика
проверки, обученные на **синтетической** истории. Реальная история обращений акимата появится в пилоте.

| Что | Статус | Где |
|---|---|---|
| Территории | **real** — 2334 объекта OSM из данных R12 (дворы, остановки, площадки, парки, места для мусора, участки крупных улиц) | `data/targets.json`, `targets.py` |
| Погода | **synthetic** фикстура по нормам Астаны, пока нет LOCAL-9; реальный архив Open-Meteo подхватывается сам | `data/weather_fixture.csv`, `weather.py` |
| История жалоб 2024-01 … 2026-10 | **synthetic, demo** | `history.py` |
| Признаки, модели, проверка | код | `features.py`, `model.py`, `backtest.py`, `RESULTS.md` |
| Прогноз для API и «Картины дня» | код + кэш | `ui/civic_forecast/` |

## Генератор истории (history.py)

Для каждой территории t, месяца m и категории c (12 категорий из `research/round-14/categories_v2.json`):

    λ = база(вид территории, c) × склонность(t) × сезон(c, погода месяца m) × рост платформы(m)
        × горячий эпизод × всплеск × стройка рядом;      жалоб ~ Пуассон(λ)

- **база** — сколько жалоб в месяц типично для вида: у двора — дворы, мусор, ЖКХ, парковки; у остановки — транспорт
  и снег; у участка улицы — ямы, тротуары, снег; у площадки для мусора — мусор и запахи (таблица `BASE`).
- **склонность** места — логнормальная (σ = 0.55): есть «вечные» проблемные дворы, но их немного.
- **сезон** от погоды месяца: снег и гололёд — снегопад и оттепели (ноябрь–март); отопление — старт сезона в октябре
  и ноябре, мороз; ямы — весна после таяния, сильнее после оттепелей прошлого месяца; мусор и запахи — летняя жара;
  освещение — длинные ночи; дворы и площадки — тёплый сезон; транспорт — сентябрь и холод.
- **горячие места**: эпизод начинается с вероятностью 3 % в месяц, длится в среднем 3 месяца, ×5 на 1–2 категориях.
- **всплески**: 1,5 % «территория × месяц», одна категория ×6.
- **стройки**: 40 синтетических строек на 3–9 месяцев; в радиусе 400 м растут дороги, тротуары, шум и пыль.
  План строек известен заранее (в пилоте — реестр R06 с этапом «Строительство»).
- **рост платформы**: +1,5 % жалоб в месяц (жителей на платформе становится больше).
- Детерминированность: у каждой территории свой генератор с seed от (`SEED` = 2026, id) — подмножество территорий
  даёт те же числа, что и полная история.

Параметры подобраны так, чтобы задача не была тривиальной. В первой версии (σ = 0.8, эпизоды 2 %/мес ×4, порог 3)
даже прогноз «как в прошлом месяце» давал ~90 % на top-30 — такая проверка ничего не различает.

## Признаки и модели

Признаки «территория × месяц» — только известное к концу месяца M (прогноз на M+1): жалобы за 1/3/12 месяцев и по
категориям, тот же месяц год назад, тренд, сколько месяцев подряд проблема, вид территории, район, сезон, стройка по
плану, погода прошлого месяца и **норма** прогнозного месяца по прошлым годам (фактическую погоду будущего месяца
никто не знает — в признаки она не попадает). Цель: ≥ 4 жалоб в следующем месяце (~4 % территорий).

- `gbm` — HistGradientBoostingClassifier (scikit-learn 1.9).
- `fallback` — без зависимостей: уровень категории без сезона × сезон прогнозного месяца + тот же месяц год назад,
  вероятность P(Пуассон(λ) ≥ 4).
- базовые: `last_month`, `same_month_ly`.

## Проверка

`python3 -m ml.civic_forecast backtest --seeds 2026,2027,2028` — для каждого месяца 2025-07 … 2026-10 модель
обучается только на прошлом, называет top-K, считается доля подтвердившихся (precision@K). Таблица — `RESULTS.md`.

## Что поменяется на реальных данных (план пилота)

1. Заменить генератор выгрузкой обращений акимата (те же агрегаты «территория × месяц × категория»); привязка к
   территории — R12 (`engine/civic_geo`), категории — модель R03/R04.
2. Погода — LOCAL-9 (реальный архив Open-Meteo) уже поддержан загрузчиком.
3. Стройки — из реестра R06 (`ui/civic_store`, этапы объектов).
4. Пересчитать backtest; честно сравнить с базовыми; при нехватке истории (< 12 месяцев) использовать `fallback`.
