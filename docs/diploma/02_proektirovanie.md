## 2.1. Требования

### 2.1.1. Сценарий, вокруг которого построены требования

Главный пользователь демонстрации — акимат на ноутбуке; главный пользователь в жизни — житель с телефоном. Сквозной сценарий (CONTRACT §0), который должен проходить от начала до конца за 3 минуты:

1. Житель пишет жалобу (на казахском, русском или вперемешку) и выбирает место на карте; система предлагает объект: «Это здесь?» — остановка, участок улицы или двор.
2. Модель определяет категорию и находит похожие обращения; житель может нажать «Я тоже» вместо новой жалобы.
3. На карте акимата объект, участок или двор плавно краснеет — видно, где больше всего жалоб.
4. «Картина дня»: аким за 10 секунд видит темы, районы, горячие места, просрочки и объекты с отставанием.
5. Акимат предлагает решение — ставит на 3D-карту объект (сквер, площадка, спортплощадка, остановка, освещение), он «строится» с пометкой «проект»; жители голосуют.
6. После ремонта объект становится зелёным «исправлено», житель видит статус.

Фокус-район для крупного плана — Нура; остальной город работает так же.

## 2.2. Роли пользователей

| Роль | Устройство | Что делает | Главная кнопка |
|---|---|---|---|

## 2.3. Архитектура

Система спроектирована как **модульный монолит**: один процесс Python отдаёт статику и API, модули ролей — независимые пакеты Python и JavaScript-модули с общим контрактом.

[РИСУНОК 2.2: схема модулей — взять Mermaid-диаграмму из `docs/birge/ARCHITECTURE.md` §2.]

Ключевые архитектурные решения и их причины:

1. **Только стандартная библиотека на сервере** (`http.server.ThreadingHTTPServer`), без веб-фреймворка. Причина — запуск на ноутбуке акимата одной командой без сложной установки; геомодуль R12 и хранилища тоже на стандартной библиотеке.
2. **Шлюз API v2 с таблицей «маршрут → роль → модуль → функция»** (`V2_HANDLERS` в `ui/web_server.py`). Шлюз проверяет вход (границы Астаны, категории из JSON, диапазоны), модули только считают. Модуль, которого ещё нет в сборке, честно отвечает 503 `module_not_ready`, а не ломает страницу; `GET /api/civic/v2/modules` показывает состояние.
3. **Без фронтенд-фреймворка и сборки**: каждый модуль — файл JavaScript с глобальным объектом и методом `mount({root, map, api, lang, ...})`. Модули общаются событиями браузера (`birge:complaint`, `birge:lang`, `birge:open-target`). Это позволило 12 ролям разрабатывать модули параллельно и подключать их по одному.
4. **Одна карта MapLibre GL JS** на странице; модули (карта R12, тепловая карта R07, 3D-превью R05) добавляют свои слои в карту хоста, а не создают свои.
5. **ML — офлайн-обучение, онлайн-вывод на CPU**: тяжёлая модель обучается на ноутбуке с GPU, в приложение попадает ONNX int8; у каждого ML-вызова есть запасной путь без нейросети.
6. **Числа считает код**: вес тепловой карты, KPI картины дня, отставание объекта — детерминированные функции с тестами; языковая модель в рантайме не используется.

## 2.4. Модель данных

### 2.4.1. Цель привязки (CONTRACT §4)

```json
{"kind": "object|segment|area", "id": "строка", "label_ru": "Остановка «…»", "label_kk": "…"}
```

| Вид | Что это | Формат id | Источник |
|---|---|---|---|
| `object` | реальный точечный или площадной объект: остановка, детская площадка, спортплощадка, парк, место сбора мусора | `osm-node-<id>`, `osm-way-<id>` | OpenStreetMap |
| `segment` | участок улицы — ребро пешеходного графа с настоящей геометрией | `osm-w<way>-<n>` | граф `osm-astana-walking-20260506` (94 089 рёбер) |
| `area` | двор (жилой квартал) или ячейка ~150 м, где двора нет | `yard-<id>`, `cell-<ix>-<iy>` | OSM `landuse=residential`; регулярная сетка |

Выбор вида цели зависит от категории (`target_kinds` в `categories_v2.json`): дороги и тротуары → участок улицы; остановки → объект; дворы → объект или двор; ЖКХ и запахи → область.

### 2.4.2. Запись обращения (CONTRACT §5)

```json
{
  "id": "c-…", "created_at": "2026-10-11T10:00:00+05:00",
  "text": "…", "lang": "ru|kk|mixed",
  "category": "roads", "category_source": "resident|model|staff",
  "model": {"label": "roads", "score": 0.91, "version": "…", "needs_review": false},
  "point": [71.43, 51.12], "target": {"kind": "segment", "id": "osm-w123-4"},
  "district": "nura", "status": "new|accepted|in_progress|fixed|rejected",
  "status_history": [{"at": "…", "status": "new"}],
  "metoo": 3, "duplicate_of": null, "demo": true
}
```

Проектные решения записи:
- `category_source` разделяет выбор жителя, подсказку модели и решение сотрудника — это нужно и для аудита, и для будущего дообучения модели на исправлениях сотрудников;
- `model` хранит версию модели и флаг `needs_review` — видно, какая модель предложила категорию;
- `status_history` позволяет восстановить состояние на любую прошлую дату (используется «Картиной дня» для сравнения с прошлой неделей);
- `metoo` — число присоединившихся, а не отдельные записи; `duplicate_of` — ссылка на исходное обращение;
- `demo` — обязательная пометка синтетики.

### 2.4.4. Предложение, голос, этапы объекта

- Предложение: `{id, kind, geometry, title_ru, title_kk, status: proposal|approved|rejected|withdrawn, votes_up, votes_down, planned_year}`; виды — `square`, `playground`, `sports`, `stop`, `lighting` (R05/R06).
- Голос: пара «предложение + хэш устройства» уникальна; значение ±1; повторное нажатие той же кнопки ничего не меняет, другой — меняет голос.
- Этапы объекта: `planned → design → procurement → construction → acceptance → operating`; `planned_end`, `forecast_end`, вычисляемые `delay_days` и `stale` (> 14 дней без обновления). История этапов и решений по предложениям только дополняется (запрет UPDATE/DELETE триггерами SQLite).

## 2.5. Вес и цвет на тепловой карте (CONTRACT §6)

Вес цели — сумма вкладов её обращений с затуханием:

$$ w(\text{цель}) = \sum_{i} (1 + m_i)\cdot 0.5^{\,a_i / 14}, $$

где $a_i$ — возраст обращения в днях, $m_i$ — число «Я тоже», 14 дней — период полураспада (`weight_half_life_days`). Учитываются только открытые обращения (`new`, `accepted`, `in_progress`).

| Уровень | Вес | Цвет | Подпись |
|---|---|---|---|
| 0 | 0 | нет | нет жалоб |
| 1 | 1–2 | `#FAC775` | 1–2 |
| 2 | 3–5 | `#EF9F27` | 3–5 |
| 3 | 6–9 | `#E24B4A` | 6–9 |
| 4 | 10+ | `#A32D2D` | 10+ |
| исправлено | — | `#639922` | 7 дней после `fixed`, вес 0 |

Почему так:
- экспоненциальное затухание даёт «остывание» без резкого обрыва окна — цель, о которой перестали писать, плавно бледнеет;
- на значке показывается **число людей** без затухания («Сообщили 12 человек · за 14 дней») — цвет говорит «насколько горячо сейчас», число — «сколько людей»;
- цвет никогда не один: уровень = цвет + число, «исправлено» = цвет + ✓ + слово;
- для районов (мелкий масштаб) пороги умножены на 5 (решение R07), иначе весь город был бы тёмно-красным.

## 2.6. Программный интерфейс (CONTRACT §7)

Все маршруты — под `/api/civic/v2/`.

| Метод и путь | Владелец | Ответ |
|---|---|---|
| `POST /classify {text}` | R04 (модель R03, запасная v1) | `{category, score, needs_review, model_version, top3}` |
| `POST /similar {text, point?, days?}` | R04 | `{matches:[{complaint_id, score, target, metoo}]}` |
| `GET /targets?lon&lat&category` | R12 | `{candidates:[{target, distance_m, geometry}]}` |
| `POST /complaints`, `GET /complaints?bbox&since`, `POST /complaints/{id}/metoo`, `POST /complaints/{id}/status` | R09 | запись §2.4.2 |
| `GET /heat?bbox&days&category&zoom` | R07 | `{generated_at, items:[{target, geometry, weight, level, count, fixed_until}]}` |
| `GET /akim/summary?date&district` | R08 | темы, районы, топ-10 целей, просрочки, объекты с отставанием |
| `GET/POST /proposals`, `POST /proposals/{id}/vote` | R06 | `{id, kind, geometry, status, votes_up, votes_down}` |
| `GET /objects?bbox`, `PUT /objects/{id}/stage` | R06 | объект + `stage`, `planned_end`, `forecast_end`, `delay_days`, `stale` |

Принципы API: JSON; ошибки — `{"error": "<код>", "field": "<поле>"}` с кодами HTTP 400/403/404/409/422/429/503; публичные ответы никогда не содержат текст чужой жалобы, точку автора и идентификатор устройства; изменяющие действия сотрудника требуют сессию и CSRF. Ревью безопасности показало, что требование о точке автора в сборке B2 выполнено не полностью (точка отдаётся с точностью ≈ 10 см, а поиск похожих — с расстоянием до 0.1 м); исправление — огрубление до ≈ 100 м для других жителей — применено в FINAL-кандидате (глава 5, §5.7).

## 2.7. Решения по интерфейсу (UX)

Требование владельца: «Мелкие моменты важнее самого кода. Дизайн светлый и понятный, как 2ГИС, чтобы нравился людям от 5 до 40+ лет» (`UX_BRIEF.md`).

1. **Как 2ГИС**: карта на весь экран, поиск сверху, по нажатию на объект выезжает карточка — справа на ноутбуке (панель 400 px), снизу на телефоне (шторка 120 px / 50 % / 92 % высоты).
2. **Тепловая карта объектов вместо облака точек**: краснеет сама остановка (ореол, растущий с весом), участок улицы (линия по настоящей форме, толщина растёт с весом) или двор (заливка). Новая жалоба — пульсирующее кольцо, цвет плавно перетекает за ~0.8 с.
3. **Смысловой зум**: z < 12 — районы; 12–15 — дворы и участки; ≥ 15 — отдельные объекты со значками. Так город не превращается в «кашу» значков на мелком масштабе.
4. **Житель видит ту же карту мягче** (меньше прозрачность и ореол, без пульса уровня 4) — без «паники», но с кнопкой «Я тоже».
5. **Два языка на равных**: переключатель ҚАЗ/РУС всегда в шапке, выбор запоминается; весь видимый текст — через ключи словарей; казахский пишется и проверяется человеком; вёрстка рассчитана на более длинные казахские слова на 375 px. Пример тонкого решения: вопрос мастера — «Это здесь?» / «Осы жерде ме?» без вставки названия, потому что вопросительная частица в казахском (ме/ма/бе/па) зависит от последнего слова.
6. **Простые слова**: в интерфейсе нет «ребро», «граф», «геометрия» — есть «участок улицы», «двор», «остановка»; запрещённые слова проверяются автоматически (R11 `i18n_tools.py`).
7. **Цвет + число / цвет + слово**, контраст ≥ 4.5:1: исходные цвета уровней 3 и «исправлено» не дают нужного контраста с текстом, поэтому у значков с числом взяты более тёмные оттенки (`#C93B3A`, `#4E7D1A`), а на карте — исходные.
8. **Ни одного пустого экрана**: скелетон при загрузке, «пока пусто» с подсказкой, «Нет связи. Повторить».
9. **Одна главная кнопка на экране**; кнопки — глагол + 1–3 слова («Сообщить о проблеме», «Я тоже», «Взять в работу»).
10. **Дизайн-система** (R11): токены (цвета, шрифт Inter под именем «Birge Sans» с казахскими буквами, отступы, тени, анимации 200–800 мс), около 48 компонентов с префиксом `bk-`, 49 иконок; `prefers-reduced-motion` отключает анимации.

## 2.9. Безопасность и персональные данные (проектный уровень)

[ТРЕБОВАНИЕ ВУЗА: нужен ли отдельный раздел «Безопасность» / «Охрана труда» / «Экономическое обоснование».]

- Закон РК «О персональных данных и их защите» [ПРОВЕРИТЬ ИСТОЧНИК]: в системе не собираются имена и телефоны жителей; житель идентифицируется случайным идентификатором устройства, на сервере хранится только `sha256(соль + id)`, соль — только в базе.
- Публичные ответы не раскрывают текст чужих жалоб; жители видят «Сообщили N человек». Точка автора другим жителям показывается с точностью области (≈ 100 м): в сборке B2 этого ещё не было (ревью R15, находки S03 и S13), исправление применено в FINAL-кандидате.
- Подсказка в форме «Не пишите телефон и ИИН»; тексты из анонимной формы обезличиваются до использования (регулярные выражения: ИИН, телефоны, email, госномера, адреса, имена по явным шаблонам).
- Сервер: только локальный адрес, проверка Host и Origin, заголовки `nosniff`, `X-Frame-Options: DENY`, CSP `frame-ancestors 'none'`, лимиты размера запросов и частоты (20 жалоб в час с устройства, 30 голосов в минуту с адреса).
- Ревью безопасности выполнила отдельная роль проекта R15 (ИИ-агент, не писавший код модулей) (глава 5, §5.7): критичных находок нет; важные — подпись места из запроса жителя видна всем, точка жителя восстанавливается до метра, нет лимита голосов и «Я тоже» с одного адреса, обезличивание пропускает ФИО с отчеством. На каждую есть тест и patch, все применены интегратором в FINAL-кандидате (тесты R15 — 99 из 99); проектное правило по итогам ревью — подписи объектов только из данных карты, точка жителя для других — область ≈ 100 м, голоса жителей — «мнение», а не юридически значимое голосование, пока нет входа через eGov.

## 2.10. Организация разработки

[ТРЕБОВАНИЕ ВУЗА: допустимо ли и как описывать использование ИИ-ассистентов при разработке.]

Разработка раунда 14 велась автором с помощью ИИ-агентов для программирования (Claude Code), каждому из которых выдавалась роль с закреплёнными путями в репозитории (R01–R15, `research/round-14/CONTRACT.md` §2). Приёмы, которые сделали параллельную работу возможной:

1. **Контракт до кода** — форматы цели, записи обращения, весов и API (`CONTRACT.md`) фиксировались до начала работы; модули разрабатывались на фикстурах строго этого формата.
2. **Один писатель на путь** — каждая роль меняет только свои файлы; изменение чужого модуля передаётся интегратору в виде patch.
3. **Отдельная ветка на роль** и закреплённые SHA поставок; интегратор переносит поставки по путям (`git checkout <sha> -- <пути>`), без слияния веток целиком.
4. **Обязательная поставка**: `DELIVERY.json` (SHA кода и проверки, результаты тестов PASS/FAIL/NOT_RUN, ограничения), инструкция запуска, точки интеграции, handoff для продолжения другим аккаунтом.
5. **Честность**: `NOT_RUN` с причиной вместо выдуманного `PASS`; синтетика всегда помечена.

Автор выступал в роли владельца продукта и архитектора: формулировал цели и требования, принимал решения по спорным вопросам, проверял результаты и казахские тексты.
