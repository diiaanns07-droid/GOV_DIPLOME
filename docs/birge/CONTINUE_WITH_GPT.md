## 1. Что прочитать ИИ перед любой задачей (5 минут)

Скопируйте ИИ этот список как первое сообщение, если он работает с репозиторием:

1. `docs/birge/ARCHITECTURE.md` — модули и поток данных.
2. `docs/birge/MODULES.md` — раздел нужного модуля: файлы, функции, тесты, ограничения.
3. `research/round-14/CONTRACT.md` — форматы записи жалобы (§5), цели (§4), веса тепловой карты (§6), API (§7), точность карты (§8).
4. `research/round-14/UX_BRIEF.md` и `research/round-14-results/R11/UX_SPEC.md` — если задача касается экрана.
5. `research/round-14/categories_v2.json` — 12 категорий; **не копировать список руками в код**.
6. `CLAUDE.md` в корне — общие правила работы агентов (они же действуют для GPT/Codex).

## 2. Правила (из CLAUDE.md и research/round-14/COMMON.txt)

### Git

- Не работать в `main`. Каждая задача — своя ветка: для Codex — префикс `codex/` (например `codex/fix-heat-legend`).
- Не делать force push, не менять чужие ветки, не сливать чужие ветки целиком.
- Не делать `git add .` вслепую — добавлять только файлы задачи. Перед коммитом смотреть `git diff --cached --stat`.
- Commit ≠ push. Если push не прошёл — не писать, что работа на GitHub.
- В отчёте всегда: ветка, SHA, статус push, что проверено, следующий шаг.
- Слияние в `main`, настройки GitHub, публикация — только отдельным решением владельца.

### Секреты и данные

- Не читать и не печатать `.env`, токены, cookies. Ключи API задаются только переменной окружения в окне терминала:
  PowerShell `$env:OPENAI_API_KEY="..."` — и никогда не записываются в файлы репозитория.
- Не коммитить: реальные обращения с персональными данными (ИИН, телефоны, имена, точные адреса), `venv`, кэш, `*.sqlite3`, модели > 50 МБ.
  Сырые ответы Google-формы лежат в `private/` (папка в `.gitignore`).
- Синтетика остаётся синтетикой: записи с `demo: true` и наборы `synthetic` **никогда** не переименовываются в реальные.
  Реальные объекты OSM — `real`. Если не уверен — пометить и спросить владельца.

### Качество (слова владельца)

- «Мелкие моменты важнее самого кода; всё должно работать очень чётко; точность карты важна».
- Простой читаемый код, комментарии по-русски в сложных местах.
- Тестировать реальные риски: неверная геометрия, пустые данные, ошибки сети, переключение языка ҚАЗ/РУС, экран 375 px.
- `NOT_RUN` с причиной лучше выдуманного `PASS`. Скриншоты — только реально запущенного интерфейса.

### Интерфейс (UX_BRIEF, 8 правил)

1. Как 2ГИС: карта на весь экран, карточка справа (ноутбук) или снизу (телефон).
2. Текст ≥ 16 px, кнопки ≥ 48 px, контраст ≥ 4.5:1.
3. Иконка всегда с подписью; одна главная кнопка на экране.
4. Простые слова: нет «ребро», «граф», «геометрия», «payload» — есть «участок улицы», «двор», «остановка».
5. Цвет никогда не один: уровень = цвет + число, статус = цвет + слово.
6. ҚАЗ / РУС в шапке; весь видимый текст — через ключи `web/civic/i18n/ru.json` и `kk.json` (оба файла сразу).
7. Ни одного пустого экрана: загрузка, «пока пусто», ошибка с действием «Повторить».
8. Анимации 200–800 мс; карта не двигается сама, если пользователь её трогает.

### Точность карты (CONTRACT §8)

- Никаких линий «от руки»: участок улицы = рёбра графа `engine/civic_scenarios/graphs/osm-astana-walking-20260506.graph.json` между двумя точками.
- Точечные объекты — только реальные из OSM.
- Тесты: линия участка ≤ 5 м от формы ребра; остановка ≤ 60 м от улицы; всё внутри границы Астаны.
- Нет точного места — показываем область «примерное место».

### Владение путями

Раунд 14 закрепил пути за ролями (`research/round-14/CONTRACT.md`, §2). После 15 октября ролей нет, но **правило одного писателя** остаётся: в одной ветке/папке одновременно работает один агент. Если задача трогает два модуля — сначала один, потом второй, отдельными коммитами.

## 3. Как давать задачу ИИ — шаблоны промптов

Во всех шаблонах замените `<...>`. Первый абзац одинаковый — он задаёт правила.

**Общая шапка (вставлять в начало каждого промпта):**

```
Репозиторий GOV_DIPLOME (проект Birge). Работай в ветке codex/<короткое-имя> от <базовая ветка или SHA сборки>.
Сначала прочитай docs/birge/CONTINUE_WITH_GPT.md (правила), docs/birge/ARCHITECTURE.md и раздел модуля <модуль> в docs/birge/MODULES.md.
Не читай .env. Не меняй файлы вне перечисленных путей. Коммить только изменённые файлы задачи, без git add .
В конце: ветка, SHA, статус push, какие тесты запущены и их результат (PASS/FAIL/NOT_RUN с причиной), что осталось.
```

### 3.1. Исправить баг

```
<общая шапка>
Задача: исправить баг в модуле <модуль> (пути: <пути из MODULES.md>).
Что происходит: <шаги воспроизведения, что видно, скриншот или текст ошибки из консоли/терминала>.
Что должно быть: <ожидаемое поведение>.
Порядок:
1) Воспроизведи баг тестом (добавь тест в tests/civic/<папка модуля>/), убедись, что он падает.
2) Исправь минимально, не трогая чужие модули. Комментарии по-русски в сложных местах.
3) Запусти тесты модуля (команда в MODULES.md) и тесты соседей, которые его используют.
4) Если баг в интерфейсе — проверь 375 px и 1366 px, обе локали ҚАЗ/РУС.
```

```

для проверки владельцем, не выдумывай.
Состояния: загрузка (скелетон), пусто (подсказка), ошибка («Нет связи. Повторить»), успех.
```
